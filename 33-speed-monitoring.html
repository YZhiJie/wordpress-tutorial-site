第 33 章 速度测试与持续监控 ​

🟡 中级难度 ｜ 一句话导览：性能优化（第 29 章）解决「怎么改」，本章解决「怎么测、怎么盯」——逐个工具讲清 PageSpeed Insights、WebPageTest、GTmetrix、Chrome DevTools 的点击级用法与瀑布图读法，建立 Core Web Vitals 现场数据意识与性能预算，最终落成「每次变更都测速」的持续监控习惯。

学习目标 ​

  • 分清实验室数据（Lab Data）与现场数据（Field Data）的区别与各自用途
  • 会用 PageSpeed Insights、WebPageTest、GTmetrix 各跑一次完整测试并读关键指标
  • 能读瀑布图：从 TTFB、阻塞请求、长任务定位瓶颈层
  • 知道 Core Web Vitals 现场数据来源（CrUX、GSC）与达标阈值
  • 会为站点建立性能预算并写进验收标准
  • 掌握持续监控工具链：GSC 周报、UptimeRobot、Query Monitor、慢日志
  • 建立「测→找瓶颈→改→复测→记录」的迭代流程

33.1 两类数据：实验室 vs 现场 ​

33.1.1 原理说明 ​

测速数据分两类，混淆它们是新手最常见误区：

类型来源优点局限
实验室数据（Lab）在固定设备/网络/地点下人工跑一次测试（Lighthouse、WebPageTest 默认模式）可重复、变量可控、适合对比「改前改后」不代表真实用户：你的访客可能是 4G 旧安卓
现场数据（Field）真实用户浏览器上报（CrUX、RUM）真实分布、Google 排名参考的就是它有延迟（28 天滚动窗口）、无明细瀑布图

工作方式：优化时用实验室数据快速迭代，验收时看现场数据。实验室分数漂亮而现场数据不达标，说明真实用户的网络/设备比测试环境差，要在测试档位上「加难度」再优化。

33.1.2 工具选型决策 ​

mermaid
flowchart TD
    Q{我要做什么?} -->|快速体检/给客户看分| A[PageSpeed Insights]
    Q -->|深度定位瓶颈/改前改后对比| B[WebPageTest]
    Q -->|看长期趋势图表| C[GTmetrix 历史记录]
    Q -->|INP 差/JS 卡顿| D[DevTools Performance]
    Q -->|找没用的 CSS/JS| E[DevTools Coverage]
    Q -->|查真实用户指标| F[GSC 核心网页指标 / CrUX]
    Q -->|查站内慢查询| G[Query Monitor]

一个熟手的日常其实只用三个：WebPageTest（深度）+ PSI（快检）+ GSC（验收），其余按需取用。

再补充一个常见误区：不要用「首页秒开」的浏览器体感代替工具测量——你的浏览器有缓存、有预热、在同一网络下，体感几乎必然是快的。工具的价值正是模拟「第一次来访的陌生用户」，那才是大多数访客的真实体验。

33.2 测速工具全家桶 ​

33.2.1 PageSpeed Insights（PSI） ​

访问 pagespeed.web.dev，输入 URL → 分析。报告分两大块：

  • 顶部「实测数据」：来自 CrUX 的现场数据（流量不足的站点没有，只显示实验室数据）。看 LCP/INP/CLS 三个圈是否绿色；
  • 下方「性能」：Lighthouse 实验室跑分（0~100），以及「诊断」区的具体改进建议（如「移除阻塞渲染的资源」「适当地调整图片大小」——每条都可展开看到涉及的具体文件）。

点击要点：分别测移动端和桌面端（默认移动）；每次测试是单次采样，波动 ±5 分正常，别纠结个位数。

33.2.2 WebPageTest（深度分析首选） ​

访问 webpagetest.org，它的强大在于可控变量：

  1. Location：选离目标用户近的节点（如东京、法兰克福）；
  2. Connection：选档位（建议 4G / Cable 各跑一次）；
  3. Advanced Settings → Number of Tests：设为 3——跑 3 次取中位数，排除偶发抖动；
  4. Repeat View：勾选后同时给出「首次访问」与「二次访问（有浏览器缓存）」对比，直接验证你的静态缓存配置是否生效。

跑完重点看：瀑布图（33.3 详解）、首屏视频对比（Filmstrip）、Web Vitals 一栏的 LCP 元素标注（它会用红框标出 LCP 元素是谁）。

33.2.3 GTmetrix ​

gtmetrix.com 免费版提供固定节点的 Lighthouse 报告 + 瀑布图，界面比 WebPageTest 友好，历史记录图表适合向客户展示趋势。专业版可多节点与监控告警。读法与 WebPageTest 相通。

33.2.4 Chrome DevTools Performance 面板 ​

当瓶颈在前端 JS 执行（INP 差）时，瀑布图看不出细节，要用 DevTools：

  1. F12 打开 DevTools → Performance 面板；
  2. 点录制按钮（圆形），操作页面（如点击菜单、滚动），点停止；
  3. 时间轴上找红色标记的长任务（Long Task，>50ms 的色块）；
  4. 展开长任务看调用栈：哪个脚本、哪个函数占住了主线程——WordPress 站点常见元凶是页面构建器的滑块/动画库。

辅助面板：Network 面板勾「Disable cache」模拟首次访问，按 Waterfall 列排序找最慢请求；Lighthouse 面板可本地直接跑分（隐身窗口跑，排除浏览器扩展干扰）。

33.2.5 Lighthouse 评分构成（知道分数从哪来） ​

Lighthouse 性能总分 0~100 由五项指标加权合成（v12 权重）：

指标权重含义速记
LCP25%最大内容绘制
INP30%交互响应（实验室环境用 TBT 总阻塞时间近似）
CLS25%布局稳定性
FCP10%首次内容绘制
SI（Speed Index）10%页面视觉填充速度

启示：TBT/INP、LCP、CLS 三项占 80%——主线程 JS 瘦身、大图优化、布局稳定就是提分的全部主战场；FCP/SI 会随前三项改善自然变好。

33.2.6 WebPageTest 高级功能 ​

WebPageTest 还有三个值得知道的能力：

  1. 视频对比（Visual Comparison）：把两次测试（改前/改后）的 Filmstrip 并排播放，直观看到「哪个时刻画面填充到什么程度」——向非技术同事或客户解释优化成果时，这段视频比任何数字都有说服力；
  2. 脚本化测试（Script）：可写脚本先登录、再测登录后页面（如会员中心），或先滚动再测懒加载行为。登录态测试是页面缓存 bypass 场景下唯一的实验室验证手段；
  3. 自定义指标与请求拦截：可屏蔽特定域名（如停掉第三方统计脚本）测「没有它我们会多快」，用于评估第三方资源的真实代价。

33.2.7 DevTools Coverage：揪出「加载了但没用」的代码 ​

页面构建器类主题常一次加载几百 KB 的 CSS/JS，而当前页面只用了一小部分。Coverage 面板能量化这件事：

  1. DevTools → 右上角 ⋮ → More tools → Coverage；
  2. 点录制按钮并刷新页面，面板列出每个 CSS/JS 文件的「未使用字节数」与占比红色条；
  3. 按 Unused Bytes 降序排：未使用率 > 70% 的大文件就是优化对象——要么条件加载（第 25 章），要么换更轻的插件/主题方案。

注意：Coverage 是「本次页面浏览」的统计，交互后才执行的 JS（如弹窗）会被误标为未使用，判断时先完成页面上的主要交互再停止录制。

33.2.8 测速工具速查表 ​

工具数据类型强项局限成本
PageSpeed Insights实验室+现场一键两看，有改进建议清单单次采样波动大免费

33.2.9 Lighthouse CI（概念） ​

把 Lighthouse 跑分接入持续集成：每次代码推送自动测试，分数低于预算则构建失败。适合有开发流程的团队站，个人站了解概念即可——配置方式是 GitHub Actions 跑 @lhci/cli，对接公开 URL 或预发环境。

33.3 瀑布图读图训练 ​

33.3.1 原理说明 ​

瀑布图（Waterfall）按时间轴画出页面每个请求的「排队→DNS→连接→TLS→等待→下载」各阶段。读它是性能分析的基本功，三种典型病灶：

mermaid
flowchart TD
    A[瀑布图异常] --> B[TTFB 长<br/>第一个请求「等待」段占大头]
    A --> C[阻塞请求<br/>CSS/JS 下载完前页面白屏]
    A --> D[长任务<br/>下载早但执行慢, INP 差]
    B --> B1[病灶: 服务器慢/缓存未命中<br/>→ 回第 29 章分层模型]
    C --> C1[病灶: 渲染阻塞资源多<br/>→ 关键 CSS + 延迟 JS]
    D --> D1[病灶: JS 臃肿<br/>→ DevTools 定位长任务脚本]

33.3.2 读图三步法 ​

  1. 看第一个请求（HTML 文档）：它的「Waiting / TTFB」段若 > 600ms，说明服务器响应慢——缓存未命中或源站本身慢。对照 第 29 章 分层模型逐层查：FastCGI 缓存是否 HIT、OPcache 是否开、SQL 是否慢；
  2. 看渲染前的阻塞区：LCP 时间点之前，有多少 CSS/JS 是必须等的？非关键的（页脚统计代码、延迟可用的轮播库）应 defer/异步；
  3. 看请求队列的形状：正常是「前陡后缓」——关键资源早且集中，长尾少量懒加载请求。若中段突然冒出几十个小图/字体排队，检查是不是装饰图没懒加载、或字体文件没子集化。

瀑布图每行请求的色段含义（WebPageTest/GTmetrix 通用约定）：

色段含义异常信号
DNS 查询域名解析> 100ms 或第三方域名过多
连接/TLSTCP 握手与 TLS 协商每个新域名都要付一次，第三方域名多则累计可观
等待（TTFB）服务器处理中首个 HTML 的这段是本章头号关注对象
下载内容传输大文件这段长 → 压缩/瘦身问题

33.3.3 练习判例 ​

瀑布图特征诊断去处
HTML 的 TTFB = 2.8s，二次测试仍 2.7s页面缓存没命中，每次都跑 PHP第 29 章 29.3 节
TTFB 60ms，但一张 3MB 横幅图下载 4s图片未优化，LCP 被拖死第 30 章
资源都很快，LCP 晚：首屏 CSS 加载完前全白渲染阻塞，缺关键 CSS第 29 章 29.5 节
一切下载快，但点击菜单延迟半秒长任务占主线程，INP 问题DevTools Performance 定位脚本

33.3.4 读图常见误区 ​

  • 误区一：请求数越少越好。HTTP/2 下 60 个小请求与 20 个差别不大，重要的是阻塞路径上的请求数与关键资源大小；
  • 误区二：只看总加载时间（Load）。懒加载普及后 Load 时间参考价值下降，应看 LCP 与 Speed Index；
  • 误区三：忽略第三方域名。瀑布图右侧的 Domain 列按域名聚合，第三方脚本的真实占比一眼可见——很多「我的站不重」的错觉来自没把第三方算进去。

33.4 Core Web Vitals 现场数据 ​

33.4.1 数据来源与达标线 ​

  • CrUX（Chrome User Experience Report）：Chrome 匿名汇总真实用户的 LCP/INP/CLS，是 Google 排名的直接参考；
  • GSC 核心网页指标报告：Search Console → 体验 → 核心网页指标，按「不良/需要改进/良好」分组列出具体 URL——这是你应该每周看的报告；
  • 达标标准（按第 75 百分位，即 75% 的真实访问达标才算过）：
指标良好需要改进不良
LCP≤ 2.5s2.5~4s> 4s
INP≤ 200ms200~500ms> 500ms
CLS≤ 0.10.1~0.25> 0.25

⚠️ 现场数据是 28 天滚动窗口：今天改了优化，GSC 报告要两三周才完全反映。别改完第二天看没变就回滚。

33.4.2 CrUX 数据的深挖渠道 ​

除 PSI 页面顶部外，CrUX 数据还有两个官方入口：

  • CrUX History API / BigQuery：可查任意 origin 过去数月的指标历史，适合做同比/环比趋势图（需要一点 SQL，了解概念即可）；
  • Looker Studio 的 CrUX 连接器：建一个仪表盘绑定你的域名，自动生成 LCP/INP/CLS 的月度分布图，适合给客户做月报。搜索「CrUX Dashboard」按官方向导绑定域名即可。

33.4.3 RUM（真实用户监控）概念 ​

CrUX 只覆盖用 Chrome 且同意上报的用户，样本之外（Safari、低流量页面）需要自建 RUM：在页面注入少量 JS（如 web-vitals 官方库），把每个访客的 LCP/INP/CLS 上报到自己的分析端。概念了解即可——多数站点用 CrUX + GSC 已够；WooCommerce 等高价值站可接 SpeedCurve、Sentry Performance 等服务。

33.4.4 读现场数据的两个要点 ​

  1. 看分布而非单点：现场数据是分布——GSC 把 URL 分成「良好/需改进/不良」三桶，优化的目标是把整批 URL 从右往左挪。某个 URL 单次慢不算问题，整组进入「不良」桶才需要行动；
  2. 移动端与桌面分开看：GSC 报告默认分开统计。移动端不达标而桌面达标的站极常见，排障重心永远在移动端。

33.5 建立性能预算 ​

33.5.1 原理与示例 ​

性能预算（Performance Budget）是给页面定的「体重上限」：写下来、可验收、超标必须减回来。建议起步预算（可按站点类型调整）：

项目预算测量方式
首页总大小≤ 1.5 MB（移动端）WebPageTest Bytes In
首页请求数≤ 50 个WebPageTest Requests
LCP（移动端 4G 实验室）≤ 2.5sPSI / WebPageTest
TTFB（缓存命中）≤ 200msWebPageTest 首请求
单张正文图≤ 200KB媒体库抽查

把预算写进团队约定或外包验收单：「交付时移动端 PSI ≥ 85、首页 ≤ 1.5MB」。没有预算的网站，体积只会单向膨胀。

33.5.2 测速矩阵：别只测首页 ​

首页快不代表全站快。WordPress 站点至少应覆盖五类模板页，各类型的瓶颈往往不同：

页面类型代表 URL特有瓶颈
首页/幻灯片/横幅大图、最新文章列表查询
文章页一篇含多图的长文图片懒加载、评论加载、相关文章查询
分类归档页/category/xxx/列表查询 + 缩略图数量多
搜索结果页/?s=测试通常不走页面缓存，裸跑 LIKE 查询
联系/表单页/contact/表单插件脚本、验证码第三方请求

把五类页面各跑一次 WebPageTest 填入矩阵，瓶颈分布一目了然。预算也应按类型分别设定——归档页图多，总大小预算可比首页宽 20%。

33.5.3 预算超标怎么办 ​

预算的意义在于触发动作：月度测试发现超标 → 按瀑布图找出「新增的重量」→ 决定是优化它还是修订预算（业务确实需要那个功能时）。预算是谈判工具，不是教条——关键是每次超标都有意识地决策，而不是无声地变胖。

33.5.4 把预算变成硬约束 ​

纸面预算的宿命是被遗忘。两种硬化方式：

  1. CI 拦截：Lighthouse CI（33.2.9）里断言 budgets 文件中的上限，超标让构建变红；
  2. 变更流程卡口：团队的「装新插件 checklist」里加一条「装后跑 WebPageTest 对比并贴到记录表」（33.6.1 的变更侧监控），没有对比数据的插件变更不允许上线。

个人站做不到这么正式，至少做到：每月预算复核时翻一遍当月的变更记录，把每个超标项与某个具体变更对上号。

33.6 持续监控方案 ​

33.6.1 四层监控网 ​

mermaid
flowchart TD
    A[监控体系] --> B[搜索侧: GSC 核心网页指标周报]
    A --> C[可用性: UptimeRobot 每 5 分钟拨测]
    A --> D[服务器侧: 慢日志/资源监控<br/>Better Stack 等]
    A --> E[变更侧: 每次装插件/换主题<br/>跑一次 WebPageTest 对比]
  1. GSC 核心网页指标：每周一看，发现「不良」URL 分组及时跟进；
  2. UptimeRobot：免费版每 5 分钟 ping 一次首页，宕机邮件/短信告警。这是「可感知」与「事后才知道」的区别；
  3. 服务器监控：Better Stack（原 Logtail）、Netdata 或云厂商自带监控看 CPU/内存/磁盘趋势；配合 Nginx 日志格式中的 rt=$request_time urt=$upstream_response_time（见 nginx-wordpress.conf 头部注释）做慢请求统计；
  4. 变更前后对比习惯：每装一个插件、换一次主题、改一处缓存配置，跑一次 WebPageTest 并记录——把 33.7 的迭代流程变成肌肉记忆。

33.6.2 WordPress 侧监控：Query Monitor ​

Query Monitor 是 WP 开发者必备的调试插件（正式站短期使用，排查完停用）：

  • Queries 面板：当前页面执行了多少条 SQL、每条耗时、谁发起的（核心/插件/主题）。重复几十次的相同查询 = 该上对象缓存；单条 > 0.05s 的查询 = 慢查询嫌疑人；
  • Hooks & Actions 面板：每个钩子下挂了哪些函数、耗时分布——某个插件在 init 钩子上干重活一目了然；
  • 概览条：后台工具栏直接显示当前页 PHP 耗时、峰值内存、查询数，随手刷新即知页面「重不重」；
  • HTTP API Calls 面板：列出本页面请求发出的所有远程 HTTP 调用（许可证校验、更新检查、第三方 API）——后台莫名变卡时先看这里；
  • Conditionals 与 Environment 面板：确认当前命中的模板、PHP/MySQL 版本与关键配置，跨环境排障时省去来回猜。

⚠️ Query Monitor 本身有开销且向所有管理员暴露调试信息，正式站只在排查期间启用，用完即停用。

服务器侧补充：开启 MySQL 慢查询日志（配置见 第 29 章 29.6 节），PHP-FPM 慢日志：

ini
; php-fpm.d/www.conf：超过 5 秒的 PHP 请求记录堆栈到慢日志
request_slowlog_timeout = 5s
slowlog = /var/log/php-fpm/slow.log

33.6.3 告警分级与响应约定 ​

监控不是「收到邮件」就结束。给告警分级，避免狼来了：

级别触发条件示例响应约定
P1 紧急连续 3 次拨测失败（全站宕机）立即处理，电话/短信通知
P2 重要响应时间连续 1 小时 > 3s；磁盘 > 85%当天处理
P3 关注GSC 核心网页指标出现「不良」分组；SSL 证书 14 天内到期本周排期

约定写下来（哪怕只有你一个人）：什么级别的告警可以在深夜不处理。没有分级的监控会在三个月后被你整体静音——那等于没有监控。

33.6.4 监控数据保留与复盘 ​

UptimeRobot 免费版只保留近期数据，建议每月导出一次可用率与响应时间，与 WebPageTest 月报、GSC 指标放进同一个表格。季度复盘时回答三个问题：① 可用率是否 ≥ 99.9%（每月宕机 < 43 分钟）；② 性能趋势是变好还是变坏；③ 变差的时间点对应什么变更（插件？流量增长？主机降配？）。这就是从「被动救火」到「主动运维」的转变。

33.7 优化迭代流程 ​

33.7.1 标准五步法 ​

mermaid
flowchart LR
    A[测<br/>同点位同档位跑 3 次取中位] --> B[找<br/>瀑布图定位瓶颈层]
    B --> C[改<br/>一次只改一处]
    C --> D[复测<br/>同条件再测]
    D --> E[记录<br/>优化日志表]
    E --> A
  1. 测：固定 WebPageTest 的节点与档位，跑 3 次取中位数作为基线；
  2. 找：用 33.3 的读图法判断瓶颈在服务器层 / 图片 / 阻塞资源 / JS 执行哪一层——不要跨层乱猜；
  3. 改：一次只改一处（如「只开 FastCGI 缓存」），多处并改无法归因；
  4. 复测：同点位同档位重跑，对比 LCP/TTFB/总大小；
  5. 记录：填入优化日志（表格模板见 第 29 章 29.7 节），形成可追溯的演进史。

这套流程看似繁琐，实则省时——「凭感觉优化」的典型路径是改十处、好两处、坏三处、不知道哪里出了问题，最后全部回滚。流程化把每一步的收益都变成可验证的事实。

33.7.2 一个完整的日志实例 ​

以「首页 LCP 从 4.8s 优化到 1.9s」为例，优化日志应长这样：

  • 10-04 基线：TTFB 1200ms / LCP 4.8s / 3.2MB 86 请求（瀑布图显示横幅图 3MB、TTFB 无缓存）；
  • 10-04 开 OPcache：TTFB 420ms，LCP 4.1s → 保留；
  • 10-05 上 FastCGI 缓存：TTFB 35ms（命中），LCP 3.0s → 保留；
  • 10-06 横幅图压到 180KB + fetchpriority=high：LCP 1.9s → 达标；
  • 结论：本例中图片一步收益最大（-1.1s），缓存两步主要改善 TTFB——两类手段各司其职，不可偏废。

33.7.3 节奏建议 ​

  • 每周：GSC 核心网页指标 + UptimeRobot 报告扫一眼（5 分钟）；
  • 每月：WebPageTest 全量跑一次首页 + 一篇典型文章页，对照预算；
  • 每次变更（装插件/换主题/改缓存配置）：必跑 WebPageTest 对比；
  • 每季度：全站图片/数据库/autoload 体检（对照 第 29、30 章 清单）。

33.7.4 常见优化项的预期收益参考 ​

排期时按「收益/成本比」选先做哪个（典型 WordPress 站的经验值，供排序参考而非承诺）：

优化项实施成本典型 LCP 收益章节
图片压缩 + 转 WebP低（插件）-30%~-50%第 30 章
页面缓存（FastCGI/插件）低TTFB -80%+第 29 章
OPcache 开启/调优低TTFB -30%~-60%第 29 章
延迟非关键 JS中INP 改善明显第 29 章
换轻量主题/去页面构建器高全面改善，但工程量大—
CDN 接入低~中远端用户 TTFB 减半第 29 章

原则：先把低成本高收益的做完，再考虑换主题这类大手术。多数站点做完前三项就能达到预算线。

33.8 常见问题速查 ​

33.8.1 实验室分数 95，真实用户仍喊慢 ​

实验室默认档位可能比你的真实用户条件好。排查方向：① 访客主要地区与测试节点不一致（海外站用东京节点测，用户在拉美）；② 访客设备差（旧安卓的 JS 执行比测试模拟慢数倍）——用 WebPageTest 的低端设备模拟复测；③ 现场数据看 CrUX 的地域/设备分布，确认慢的到底是哪部分用户；④ 二次访问缓存命中率——实验室每次是冷启动，真实老用户应该更快，如果他们更慢，检查是否登录态用户全走了 bypass 缓存路径。

33.8.2 不同工具数据对不上 ​

PageSpeed 说 LCP 3.1s，WebPageTest 说 1.9s，谁对？都对——它们节点不同、网络档位不同、Chrome 版本不同，甚至跑的当天 CDN 状态不同。数据只在「同工具、同设置」下可纵向对比；跨工具只比数量级，不比小数点。选定一个主工具（推荐 WebPageTest）作为内部基准，其他作参考。

33.8.3 后台慢、前台快 ​

前台有页面缓存拦截所以快，后台每个请求都裸跑 PHP+MySQL。典型原因：① admin-ajax.php 被 Heartbeat 或插件轮询打满（降频见 第 29 章 29.4 节）；② 某插件在后台每页加载远程数据（查许可、拉新闻 feed）卡住请求——用 Query Monitor 的 HTTP API Calls 面板抓现行；③ 后台未受益对象缓存——上 Redis 对后台提速最明显。

33.8.4 监控告警「宕机」但站是好的 ​

UptimeRobot 报 down，浏览器却能开：可能是监控节点到服务器的网络抖动，或安全插件/WAF 把监控 UA 误判为攻击拦截。处理：把监控服务的 IP 段加入 WAF 白名单；告警阈值设为「连续 2 次失败才通知」过滤抖动。

33.8.5 TTFB 忽快忽慢、毫无规律 ​

典型的「缓存命中率不稳定」：① 页面缓存 TTL 太短，两次测试之间缓存过期；② 多台 PHP-FPM/多服务器架构下缓存不共享（文件缓存各存各的）——换 Redis 做集中缓存；③ CDN 各节点独立缓存，不同节点命中状态不同——属正常，看整体命中率而非单次结果；④ 心跳类请求（带 nonce/时间戳参数）天然不缓存，把它们从统计中排除再判断。

33.8.6 GSC 里 INP「不良」但实验室 TBT 正常 ​

INP 是现场指标，测的是真实交互（点击菜单、展开折叠、提交表单）的响应，实验室的 TBT 只是代理近似。排查：① 用 Chrome DevTools Performance 面板真实点击页面中的交互元素并录屏分析（33.2.4），找到该交互触发的长任务；② 常见元凶：菜单的下拉动画框架、表单验证库、页面构建器的前端脚本；③ 第三方脚本（客服聊天、热力图）只在真实环境加载，实验室可能没有——对比两次测试的域名列表。

33.8.7 优化后 WebPageTest 反而变慢 ​

先别回滚，按顺序排除：① 是否赶上了网络/节点抖动——重跑 3 次取中位再比；② 清缓存后第一次访问是「冷缓存」，比优化前的「热缓存」慢是正常的——用 Repeat View 对比或先热身再测；③ 新增的优化本身有代价（如关键 CSS 内联让 HTML 变大、OPcache 预热期），看细分指标是哪里变慢的；④ 确认只改了一处——多处改动混杂时逐一回滚定位。排除以上后确认是优化本身回退，再回滚并记录教训。

33.8.8 移动端分数远低于桌面端，正常吗 ​

正常且普遍：移动端测试档位（慢 4G + CPU 降速模拟中低端手机）天然比桌面苛刻，两者差 20~40 分很常见。以移动端为准做优化决策——多数站点移动流量已占六成以上，且 Google 索引与评估都以移动版为准（mobile-first indexing）。桌面端只需确认没有明显异常即可。

33.8.9 第三方资源拖慢，但又不能删 ​

统计代码、客服聊天、评论系统（Disqus）、验证码等第三方脚本常占掉一半以上的加载时间，但业务需要它们。缓解手段按优先级：① 延迟加载（缓存插件的 Delay JS 或 facade 模式——先显示静态占位图，用户点击才加载真组件，YouTube 嵌入适用）；② preconnect/dns-prefetch 提前建连：

html
<!-- 对必须加载的第三方域名提前完成 DNS+TLS 握手，省下 100~300ms -->
<link rel="preconnect" href="https://www.google-analytics.com">
<link rel="dns-prefetch" href="https://fonts.gstatic.com">

③ 定期用 WebPageTest 的「请求拦截」功能评估每个第三方的真实代价（33.2.6），代价大于价值的就替换或移除。

33.8.10 本地 Docker 练习站测速有意义吗 ​

有，但目标不同：本地测不出「网络与 CDN 层面」的问题，却能可靠对比「代码层面」的改动——换主题前后、开关某插件前后的相对差异在本地是可复现的。用本地环境做 A/B 筛选，候选方案再到预发/线上环境用 WebPageTest 验证绝对数值。

动手练习 ​

练-33-01（操作题）｜三工具轮测同一页面

对你的练习站首页分别用 PageSpeed Insights、WebPageTest（4G 档位、跑 3 次）、GTmetrix 各测一次。记录三者的 LCP、TTFB、总大小，填入对比表，并用 33.8.2 的知识解释数值差异的原因。

提示：测试时确保缓存已清或勾选 Disable cache，避免前一次测试缓存干扰结果。

练-33-02（分析题）｜瀑布图诊断实战

在 WebPageTest 跑一次你的练习站文章页，导出瀑布图截图并完成标注：①HTML 请求的 TTFB 段；②LCP 元素对应的请求；③任意一个渲染阻塞资源；④你认为最值得优化的一个请求及理由（写 3~5 句话）。

练-33-03（操作题）｜现场数据入口走通

把练习站（需公开可访问）接入 Google Search Console：验证所有权 → 提交站点地图（第 31 章）→ 找到「核心网页指标」报告入口。若站点流量不足无现场数据，用 PSI 测一个知名大站（如 wordpress.org），阅读其 CrUX 现场数据分布图并描述。

练-33-04（操作题）｜建立监控网

完成：①UptimeRobot 注册并对练习站建一个 5 分钟监控（手动停站 3 分钟验证告警能收到，再恢复）；②安装 Query Monitor，在后台刷新三个不同类型页面（首页/文章页/后台文章列表），记录每页的查询数与最慢查询；③写下你的站点性能预算表（参照 33.5）。

练-33-05（综合题）｜完整迭代一轮

选一个你站点当前的性能短板（例如首页总大小超预算）：执行 33.7 五步法完整走一轮——基线测试、瀑布图定位、单项修改、复测、记录。提交优化日志表格（含两次测试的 WebPageTest 报告链接或截图），并回答：如果复测结果反而变差，你的下一步是什么？

进阶挑战：把同样的迭代流程写成一个 check 清单（checklist），放在团队 wiki 或 Git 仓库，使其成为每次发布前的标准流程。
