第 19 章 性能优化插件 ​

🟡 进阶难度 ｜ 一句话导览：性能优化不是「装个缓存插件就完事」，而是理解浏览器缓存、页面缓存、对象缓存、OPcache、CDN 五层架构，按需组合。本章以 WP Super Cache 为例做点击级配置，讲透 Redis 对象缓存、数据库优化、资源压缩合并的利与弊，并给出缓存穿透、样式错乱、JS 依赖破坏三大事故的排查顺序。

学习目标 ​

  • 画出 WordPress 性能优化的五层缓存架构，理解每层的作用与适用场景
  • 完成 WP Super Cache 的简单模式配置，理解「预缓存」与「垃圾回收」的区别
  • 在服务器装好 Redis 的前提下，配置 Redis Object Cache 插件实现对象缓存
  • 掌握数据库优化：修订版本、草稿、瞬态（transient）的清理策略
  • 理解资源压缩合并的原理，以及 HTTP/2 时代「合并」是否仍然必要的争议
  • 配置延迟加载（Lazy Load）与延迟 JS，提升首屏速度
  • 遇到缓存导致登录用户看到他人页面、改 CSS 不生效、压缩合并破坏 JS 依赖时，能按层级排查

19.1 缓存分层：五层架构全景 ​

19.1.1 原理说明 ​

WordPress 的性能问题本质是「每次请求都要重复计算」：查数据库、组装页面、输出 HTML。缓存的思想是「把计算结果存起来，下次直接用」。但「存起来」发生在多个层级，每层解决不同瓶颈：

mermaid
flowchart LR
    A[用户浏览器] -->|1. 浏览器缓存<br/>静态资源本地存| B[CDN 边缘节点<br/>2. CDN 缓存<br/>全球分发]
    B -->|3. 页面缓存<br/>整页 HTML 存磁盘/内存| C[Web 服务器]
    C -->|4. 对象缓存<br/>数据库查询结果存 Redis| D[PHP/WordPress]
    D -->|5. OPcache<br/>PHP 字节码存内存| E[PHP 解释器]
层级名称存什么生效位置由谁负责
1浏览器缓存CSS/JS/图片用户电脑服务器响应头（Cache-Control）
2CDN 缓存静态资源 + 整页 HTML全球边缘节点Cloudflare/阿里云 CDN 等
3页面缓存完整 HTML 页面服务器磁盘或内存WP Super Cache 等插件
4对象缓存数据库查询结果服务器内存（Redis/Memcached）Redis Object Cache 等插件
5OPcachePHP 编译后的字节码PHP 进程内存php.ini 配置

关键认知：五层是叠加关系，不是替代关系。一个小站可能只需要第 3 层（页面缓存）+ 第 1 层（浏览器缓存）；一个高并发站可能需要全部五层。本章主要讲第 3、4 层（插件可控），第 1、2、5 层的基础配置见第 29 章。

19.1.2 操作方法：评估你的瓶颈在哪一层 ​

在动手装插件之前，先判断瓶颈：

症状大概率瓶颈层验证方法
首页打开慢，但后台不慢第 3 层（页面缓存缺失）查看页面源代码底部是否有 <!-- Cached page generated by WP-Super-Cache -->
后台列表页、搜索页慢第 4 层（对象缓存缺失）安装 Query Monitor 插件，看数据库查询次数是否 >100
所有 PHP 页面都慢，连 phpinfo() 都慢第 5 层（OPcache 未开）php -v 或 phpinfo() 查看 OPcache 是否启用
静态资源（图片/CSS）加载慢第 1、2 层（浏览器缓存/CDN）浏览器开发者工具 Network 面板看资源响应头有无 cache-control

💡 Query Monitor 是性能排查的瑞士军刀，能精确到「哪个插件的哪次查询花了多少毫秒」。本章练习会用到它。

19.1.3 常见问题 ​

问：装了页面缓存插件，后台会变慢吗？ 通常不会。页面缓存插件默认对登录用户不缓存（因为后台内容千人千面），但某些配置错误可能导致「登录用户看到他人缓存页」（19.9.1 节会专门讲）。后台慢通常是对象缓存缺失或数据库未优化。

问：CDN 和页面缓存冲突吗？ 不冲突，是互补。页面缓存解决「源站生成 HTML 慢」，CDN 解决「用户离源站远、网络延迟高」。正确姿势是：页面缓存插件生成 HTML → CDN 把 HTML 缓存到边缘节点 → 用户从最近节点获取。

19.2 页面缓存插件配置 ​

19.2.1 WP Super Cache 简单模式 ​

原理说明 ​

WP Super Cache 是 Automattic 官方出品的页面缓存插件，原理是：当匿名用户访问页面时，PHP 把生成的 HTML 存为静态文件（wp-content/cache/supercache/域名/页面/index.html）；下次访问同一页面时，Web 服务器直接返回静态文件，不再执行 PHP 与数据库查询。

它有两种模式：

  • 简单模式（Simple）：用 PHP 判断缓存文件是否存在并输出，兼容性好，速度稍慢（仍需启动 PHP）。
  • 专家模式（Expert）：用 Apache/Nginx 重写规则直接返回静态文件，完全不启动 PHP，速度最快，但需手动配置服务器规则。

操作方法：点击级配置 ​

  1. 后台「插件 → 安装插件」，搜索 WP Super Cache，安装并启用。
  2. 进入「设置 → WP Super Cache」。
  3. 「简单」标签页：
    • 「缓存启用」：勾选「启用缓存」。
    • 「缓存方式」：选择「简单（推荐）」。
    • 点击「更新」。
  4. 「高级」标签页（关键选项）：
    • 「缓存访问此站点的已知用户」：不要勾选——登录用户不缓存，避免看到他人内容。
    • 「不缓存已登录用户的页面」：勾选（默认）。
    • 「缓存重建」：勾选。缓存过期时，先生成新缓存再删旧缓存，避免访客看到「生成中」的空白。
    • 「304 浏览器缓存」：勾选。配合浏览器缓存减少重复传输。
  5. 「预缓存」标签页：
    • 「预缓存模式」：勾选。插件会按你设定的间隔自动爬取全站页面生成缓存，确保任何页面第一次访问就有缓存。
    • 「预缓存更新间隔」：默认 30 分钟。内容更新频繁的站可改为 10 分钟；静态站可改为 1440 分钟（一天）。
  6. 「垃圾回收」标签页：
    • 「缓存超时时间」：默认 3600 秒（1 小时）。过期缓存会被删除，避免磁盘占用无限增长。
    • 「计划任务」：保持默认，插件会定期清理过期文件。

图 19-1：简单模式适合绝大多数站点；专家模式需要手动配置 Nginx/Apache 规则。

图 19-2：预缓存确保「第一次访问就快」，垃圾回收防止磁盘被缓存塞满。

验证缓存是否生效：

  1. 用无痕窗口（未登录）访问首页。
  2. 查看页面源代码，拉到最底部，应看到类似 <!-- Cached page generated by WP-Super-Cache on 2026-10-04 10:00:00 --> 的注释。
  3. 再次刷新，注释时间不变，说明命中缓存。

19.2.2 W3 Total Cache 概览 ​

W3 Total Cache 是功能更全的老牌插件：页面缓存、对象缓存、数据库缓存、浏览器缓存、CDN 集成、压缩合并，一站式解决。但正因为功能多，配置复杂度高，新手容易「全开导致冲突」。建议：先用 WP Super Cache 跑通页面缓存，理解原理后再评估是否需要 W3 Total Cache 的对象缓存与 CDN 集成。

19.2.3 商用 WP Rocket 提一句 ​

WP Rocket 是付费插件（$59/年起），优势是「开箱即用」——激活后自动开启页面缓存、浏览器缓存、Gzip、延迟加载，无需配置。如果你不想研究参数、愿意付费换时间，WP Rocket 是省心之选；如果你想理解原理、控制每一层，免费插件 + 手工配置更适合学习。

19.2.4 页面缓存的排除列表配置 ​

原理：某些页面绝不能被缓存：购物车、结账页、我的账户、密码重置页——这些页面内容是用户私有的，如果缓存给另一个用户看到，就是严重的数据泄露。

操作方法：在 WP Super Cache「高级 → 拒绝的 URL 字符串」中添加：

/cart/
/checkout/
/my-account/
/wp-admin/

WooCommerce 等电商插件会自动告诉缓存插件哪些页面需要排除，但手动检查一遍更稳妥。此外，查询参数带 ?s=（搜索）或 ?add-to-cart= 的 URL 也应排除——缓存搜索结果会导致不同搜索词返回同一页面。

19.2.5 常见问题 ​

问：预缓存会把服务器爬崩吗？ 不会。WP Super Cache 的预缓存是「逐个页面、间隔几秒」的温和爬取，不是并发轰炸。但如果站点有几千个页面且服务器性能差，可把预缓存间隔拉长到 1440 分钟，或改用「仅预缓存最新文章」。

问：开启缓存后，后台发布文章前台不更新？ 检查「高级 → 不缓存已登录用户的页面」是否勾选（应该勾选）；检查「垃圾回收 → 缓存超时时间」是否过长；手动到「内容 → 删除缓存」清一次。理想配置是：发布/更新文章时插件自动清除该页面缓存（WP Super Cache 默认支持）。

19.3 对象缓存 Redis ​

19.3.1 原理说明 ​

对象缓存把「数据库查询结果」存到内存数据库（Redis/Memcached）。WordPress 的 wp_options、wp_posts、wp_postmeta 等表的查询结果，第一次查询后存入 Redis，后续相同查询直接从内存返回，不再走 MySQL。对后台列表页、复杂归档页、WooCommerce 商品筛选页提速显著。

前提：服务器必须已安装并运行 Redis 服务。本地开发可用 Docker；生产服务器可用包管理器安装（sudo apt install redis-server 或宝塔面板一键安装）。

19.3.2 操作方法：安装与配置 ​

  1. 确认 Redis 已运行：
    bash
    redis-cli ping
# 应返回 PONG
  2. 后台安装并启用 Redis Object Cache 插件（Till Krüss 版，官方库排名第一）。
  3. 进入「设置 → Redis」。
  4. 点击「启用对象缓存」。插件会自动在 wp-content/ 下生成 object-cache.php 文件（这是 WordPress 的对象缓存 drop-in 机制）。
  5. 状态应显示「已连接」，并显示 Redis 版本、内存占用、命中率。

图 19-3：启用后状态页显示连接信息与命中率，命中率 >90% 说明配置正确。

验证对象缓存生效：

  1. 安装 Query Monitor 插件。
  2. 刷新后台「文章 → 所有文章」。
  3. 查看 Query Monitor 的「数据库查询」面板，第一次刷新可能 50+ 次查询，第二次刷新应降到 10 次以内——因为大部分查询走了 Redis。

19.3.3 常见问题 ​

问：启用对象缓存后，某些插件数据不更新？ 极少数插件直接写数据库而不通过 WordPress API（如 wpdb->query 手写 SQL），导致对象缓存中的旧数据未被清除。解法：到「设置 → Redis」点击「刷新缓存」，或联系插件作者改用 wp_update_post() 等标准 API。

问：Redis 与 Memcached 选哪个？ Redis 功能更丰富（支持持久化、更复杂的数据结构），社区生态更好；Memcached 更轻量。对 WordPress 对象缓存场景，两者性能差异不大，推荐 Redis（插件支持更好）。

19.4 数据库优化 ​

19.4.1 原理说明 ​

WordPress 数据库会随时间积累「垃圾数据」：

  • 文章修订版本：每次保存草稿/更新，旧版本都保留。一篇改 20 次的文章会有 20 条修订记录。
  • 自动草稿：新建文章时自动生成的空草稿。
  • 回收站文章/评论：删除后进入回收站，30 天后才真正删除。
  • 过期瞬态（Transient）：插件缓存的临时数据，设计为自动过期，但过期后仍留在数据库。

这些垃圾数据会拖慢查询速度，尤其是 wp_posts 与 wp_postmeta 表。

19.4.2 操作方法：清理与限制 ​

限制修订版本数量（wp-config.php）：

php
// 最多保留 5 个修订版本，超出自动删除最旧的。
define( 'WP_POST_REVISIONS', 5 );

清空回收站间隔（wp-config.php）：

php
// 回收站保留 7 天，默认是 30 天。
define( 'EMPTY_TRASH_DAYS', 7 );

手动清理（WP-CLI）：

bash
# 删除所有修订版本。
wp post delete $(wp post list --post_type='revision' --format=ids) --force

# 删除所有回收站文章。
wp post delete $(wp post list --post_status='trash' --format=ids) --force

# 删除过期瞬态。
wp transient delete --expired

自动清理插件：WP-Optimize 或 Advanced Database Cleaner 可定时自动清理，但建议先用手动方式理解原理，再决定是否自动化。

图 19-4：可视化清理工具适合新手，但务必先备份数据库。

19.4.3 常见问题 ​

问：清理修订版本会影响文章内容吗？ 不会。修订版本只是「历史快照」，清理后当前内容不受影响。但清理后无法回滚到某个历史版本，所以重要文章建议先手动备份或导出。

问：瞬态清理会导致插件设置丢失吗？ 不会。瞬态是「缓存的缓存」，清理后插件会重新生成。但某些插件把重要数据误存为瞬态（设计错误），清理后需重新配置——这是插件质量问题，不是清理操作的问题。

19.5 资源压缩合并：利与弊 ​

19.5.1 原理说明 ​

压缩（Minify）删除 CSS/JS 文件中的空白、注释、缩短变量名，减少文件体积；合并（Combine）把多个 CSS/JS 文件合并为一个，减少 HTTP 请求数。在 HTTP/1.1 时代，浏览器对同一域名最多并行 6-8 个连接，合并能显著提速。

19.5.2 HTTP/2 下的争议 ​

HTTP/2 支持多路复用——同一连接可并行传输多个文件，「减少请求数」的意义大幅下降。此时合并的副作用凸显：

  • 缓存粒度变粗：合并后任何一个小文件改动，整个合并文件缓存失效，用户需重新下载。
  • 阻塞渲染：合并后的 JS 文件可能很大，浏览器下载并解析时阻塞首屏渲染。
  • 依赖顺序破坏：某些插件的 JS 依赖 jQuery，如果合并顺序错误，依赖关系断裂。

现代最佳实践：

  • 压缩（Minify）仍然推荐，无副作用。
  • 合并（Combine）谨慎使用：HTTP/1.1 站点可合并；HTTP/2 站点建议不合并，或只合并「始终一起加载」的文件（如主题核心 CSS）。
  • 优先用「延迟加载」与「异步加载」解决 JS 阻塞，而不是合并。

19.5.3 操作方法：Autoptimize 配置 ​

  1. 安装并启用 Autoptimize。
  2. 进入「设置 → Autoptimize」。
  3. 「JavaScript 选项」：
    • 「优化 JavaScript 代码」：勾选（压缩）。
    • 「合并 JS 文件」：HTTP/2 站点建议不勾选；HTTP/1.1 站点可勾选。
    • 「异步加载 JavaScript」：勾选（非关键 JS 延迟执行）。
  4. 「CSS 选项」：
    • 「优化 CSS 代码」：勾选。
    • 「合并 CSS 文件」：同上，HTTP/2 站点建议不勾选。
    • 「内联关键 CSS」：勾选。把首屏必需 CSS 直接嵌入 HTML，减少阻塞。
  5. 「图片」标签页：
    • 「延迟加载图片」：勾选。

图 19-5：压缩默认开，合并视 HTTP 版本决定，异步加载与内联关键 CSS 是首屏提速关键。

19.5.4 常见问题 ​

问：压缩合并后样式错乱或 JS 报错？ 99% 是「合并顺序破坏依赖」或「某个文件压缩后语法错误」。解法：到 Autoptimize 设置页，把出问题的文件加入「排除列表」（如 jquery.js、某个插件的 JS），或干脆关闭合并只保留压缩。

问：HTTP/2 站点真的不需要合并吗？ 不是绝对。如果站点有 50+ 个 CSS/JS 文件，即使 HTTP/2 多路复用，浏览器解析与执行的开销仍在。此时可「分组合并」：把「始终一起用」的文件合并为一组（如主题核心 + 常用插件），「按需加载」的文件保持独立。

19.6 CDN 接入简述 ​

19.6.1 原理说明 ​

CDN（内容分发网络）把静态资源缓存到全球边缘节点，用户从物理距离最近的节点获取资源，解决「用户离源站远、网络延迟高」的问题。它是五层架构中的第 2 层，与页面缓存（第 3 层）互补：页面缓存让源站生成 HTML 更快，CDN 让用户拿到资源更快。

19.6.2 操作方法：Cloudflare 免费版接入 ​

以最常用的 Cloudflare 免费版为例：

  1. 注册 Cloudflare 账号，添加你的域名。
  2. Cloudflare 扫描现有 DNS 记录，确认无误后，到域名注册商处把 NS 服务器改成 Cloudflare 分配的两个地址。
  3. 等待 NS 生效（几分钟到 24 小时），Cloudflare 自动开始代理流量。
  4. 在 Cloudflare 控制台的「缓存 → 配置」中，把缓存级别设为「标准」，浏览器缓存 TTL 设为「4 小时」。
  5. 「速度 → 优化」中可开启 Brotli 压缩与 Early Hints。

接入后，静态资源（图片/CSS/JS）会自动缓存到全球边缘节点；整页 HTML 缓存需要配置「页面规则」（Page Rules），免费版提供 3 条规则，足够覆盖「缓存全部静态资源 + 排除后台」。

图 19-6：Cloudflare 免费版即可覆盖 CDN 缓存的核心需求，页面规则控制缓存范围。

19.6.3 常见问题 ​

问：接入 CDN 后修改网站内容不更新？ CDN 缓存了旧版本。到 Cloudflare「缓存 → 配置」点「清除所有内容」，或配置页面规则把 HTML 的缓存 TTL 缩短。源站的页面缓存插件与 CDN 缓存是两层独立的缓存，清一层不清另一层是「改了不生效」的最高频原因（排查顺序见 19.9.2）。

19.7 延迟加载与延迟 JS ​

19.7.1 原理说明 ​

延迟加载（Lazy Load）让图片/视频只在「进入视口」时才加载，首屏外的资源不下载，大幅减少首屏时间。延迟 JS（Delay JS）让非关键 JavaScript 在「用户交互后」才执行（如点击、滚动），首屏渲染不被 JS 阻塞。

WordPress 5.5+ 已原生支持图片延迟加载（loading="lazy" 属性），无需插件。但延迟 JS 需要插件实现。

19.7.2 操作方法：配置延迟 JS ​

Autoptimize 的「异步加载 JavaScript」是简化版；更精细的控制用「Flying Scripts」或 WP Rocket 的「Delay JavaScript execution」功能：

  1. 安装并启用 Flying Scripts。
  2. 进入「设置 → Flying Scripts」。
  3. 「Include Keywords」：填入非关键 JS 的关键词（如 analytics、gtag、facebook-pixel、hotjar）。
  4. 「Timeout」：设置延迟时间（如 5 秒），或选择「用户交互后」。
  5. 保存后，匹配的 JS 会在页面加载完成后延迟执行。

图 19-7：把统计代码、社交分享按钮等非关键 JS 延迟，首屏速度立竿见影。

19.7.3 常见问题 ​

问：延迟 JS 后，统计代码会不会漏数据？ 会。如果用户 5 秒内就离开页面，延迟执行的统计代码可能来不及发送数据。对统计精度要求高的站点，可把延迟时间缩短到 2 秒，或只延迟「非关键」统计（如热图工具），核心统计（如 Google Analytics）保持正常加载。

19.8 用 Query Monitor 定位性能瓶颈 ​

19.8.1 原理说明 ​

所有缓存与优化都是「对症下藥」——而 Query Monitor 就是那台「诊断仪」。它在页面底部（或管理员工具栏）展示本次请求的完整性能画像：数据库查询次数与耗时、每个查询由哪个插件触发、HTTP 请求、内存峰值、加载了哪些 CSS/JS、是否命中缓存。

19.8.2 操作方法：读性能面板 ​

  1. 安装并启用 Query Monitor（官方库免费）。
  2. 以管理员身份访问前台任意页面，页面底部会出现性能面板（普通访客看不到）。
  3. 重点看四个区域：
    • 查询（Queries）：按调用者（插件/主题/核心）分组。某个插件单独贡献了 50+ 次查询？它就是优化目标。
    • 按组件的查询：直接列出「每个插件的查询耗时占比」，一眼定位最重的插件。
    • HTTP API 调用：某些插件每次页面加载都请求外部 API（如字体、授权验证），这一项会显示耗时——超过 500ms 的外部请求就是首屏杀手。
    • 缓存命中：确认对象缓存是否生效（命中率高说明 Redis 配置正确）。

图 19-8：按组件分组后，哪个插件拖慢了站点一目了然。

19.8.3 常见问题 ​

问：Query Monitor 本身会拖慢网站吗？ 它只对登录管理员生效，且收集数据有少量开销。生产站排查完可以停用；但因为它只影响管理员，留着通常也无妨。

问：面板显示「对象缓存未启用」但我装了 Redis 插件？ 检查「设置 → Redis」的状态是否为「已连接」，以及 wp-content/object-cache.php 文件是否存在。文件被安全插件或主机商清理工具误删是常见原因。

19.9 常见问题速查 ​

19.9.1 缓存导致登录用户看到他人页面 ​

现象：用户 A 登录后访问后台，退出登录；用户 B 在同一台电脑访问前台，看到用户 A 的「欢迎回来」或购物车内容。

原因：页面缓存插件错误地缓存了「登录用户的页面」，或缓存键未区分用户身份。

排查与修复：

  1. 检查 WP Super Cache「高级 → 不缓存已登录用户的页面」是否勾选。
  2. 检查「高级 → 已知用户」设置，确保「缓存已知用户」未勾选。
  3. 检查是否有插件（如某些会员插件）强制输出「私有缓存」头，与页面缓存冲突。
  4. 清空全部缓存，重新测试。

预防：任何涉及用户隐私的页面（购物车、会员中心、订单页）必须设置 Cache-Control: private, no-cache，或在缓存插件中把这些页面加入「不缓存列表」。

19.9.2 改 CSS 不生效，缓存层级排查顺序 ​

现象：修改了主题的 style.css，刷新前台样式没变。

排查顺序（从近到远）：

  1. 浏览器缓存：强制刷新（Ctrl+F5 或 Cmd+Shift+R），或开无痕窗口测试。
  2. 页面缓存插件：到 WP Super Cache「内容 → 删除缓存」清空。
  3. CDN 缓存：如果用了 Cloudflare，到控制台「缓存 → 清除所有缓存」。
  4. 服务器 OPcache：重启 PHP-FPM（sudo systemctl restart php8.3-fpm）。
  5. 对象缓存：到「设置 → Redis」点击「刷新缓存」。
  6. 主题/插件内置缓存：某些主题（如 Avada、Divi）有自己的缓存系统，需到主题设置里清空。

终极验证：在 style.css 文件内容里加一行注释 /* cache-test-20261004 */，查看页面源代码里引用的 CSS 文件内容是否包含这行注释。如果包含但样式仍未变，说明是 CSS 选择器优先级问题，不是缓存问题。

19.9.3 压缩合并破坏 JS 依赖顺序 ​

现象：开启 Autoptimize 合并后，控制台报错 $ is not defined 或 jQuery is not defined。

原因：合并后的文件中，依赖 jQuery 的插件代码排在 jQuery 库之前执行。

修复：

  1. 到 Autoptimize 设置，「排除 JavaScript 文件」中加入 jquery.js（或 jquery.min.js），让 jQuery 保持独立加载且最先执行。
  2. 或关闭「合并 JS 文件」，只保留「优化 JavaScript 代码」（压缩）。
  3. 或把出问题的插件 JS 加入排除列表，单独加载。

图 19-9：把 jQuery 与问题插件加入排除列表，是解决依赖顺序破坏的最快方法。

19.9.4 OPcache 没开启导致所有优化效果打折 ​

现象：页面缓存、对象缓存都配好了，但首次生成缓存的页面仍然很慢（TTFB 超过 1 秒）。

排查：OPcache 是 PHP 层的加速，不属于插件范畴，但它是所有优化的地基。检查方法：

bash
# 命令行检查（需服务器权限）。
php -v
# 输出中应包含 "with Zend OPcache v8.3.x"

或在网站根目录放一个 phpinfo.php（内容为 <?php phpinfo();），浏览器访问后搜索「Zend OPcache」，确认 opcache.enable 为 On。用完立即删除该文件——phpinfo 泄露大量服务器信息。

如果未开启，参考第 03 章的 PHP 配置部分，在 php.ini 中启用 zend_extension=opcache 并设置 opcache.memory_consumption=256。

动手练习 ​

练-19-01（操作题）｜配置 WP Super Cache 并验证

在练习站安装 WP Super Cache，按 19.2.1 完成简单模式 + 预缓存 + 垃圾回收配置。用无痕窗口访问首页，查看页面源代码底部是否有缓存注释；刷新后注释时间不变，截图证明缓存生效。

练-19-02（操作题）｜对比对象缓存开启前后的查询数

安装 Query Monitor 与 Redis Object Cache。先不开对象缓存，刷新后台「文章 → 所有文章」，用 Query Monitor 记录数据库查询次数；然后开启对象缓存，再次刷新同一页面，对比查询次数变化。解释为什么第二次查询次数大幅下降。

练-19-03（分析题）｜HTTP/2 下是否需要合并

用浏览器开发者工具（Network 面板）查看你的练习站：① 当前是 HTTP/1.1 还是 HTTP/2？② 首页加载了多少个 CSS 文件、多少个 JS 文件？③ 如果开启合并，预计减少多少请求？④ 结合 HTTP 版本，给出「是否合并」的结论，并说明理由。

练-19-04（故障题）｜模拟并修复缓存穿透

在练习站开启 WP Super Cache，登录管理员账号访问前台某页面，然后退出登录。用无痕窗口访问同一页面，观察是否看到「欢迎回来，管理员」等登录态信息。如果看到，说明缓存穿透；按 19.9.1 的排查顺序修复，直到无痕窗口看到的是纯匿名页面。

练-19-05（综合题）｜为一个高并发博客设计缓存策略

假设你维护一个日均 PV 50 万的科技博客，服务器配置为 4 核 8G，已开启 OPcache。请设计完整的缓存策略：① 页面缓存插件选哪个、预缓存间隔多少？② 是否上对象缓存、用 Redis 还是 Memcached？③ 是否用 CDN、缓存什么内容？④ 数据库优化策略（修订版本、清理频率）？⑤ 静态资源压缩合并策略？每一项说明「如果这一项不做，瓶颈会出现在哪一层」。
