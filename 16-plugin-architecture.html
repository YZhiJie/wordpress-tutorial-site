第 16 章 插件架构与工作原理 ​

🟡 进阶难度 ｜ 一句话导览：插件不是魔法，它只是「一个带特定头注释的 PHP 文件 + 一套钩子系统」。本章讲透插件的本质、Action 与 Filter 的原理与用法、插件加载顺序，并带你写出第一个能运行的最小插件，最后精读配套演示插件的启动文件。

学习目标 ​

  • 说清插件的本质：wp-content/plugins 下带插件头注释的 PHP 文件，以及启用/停用到底改变了什么
  • 理解钩子系统的设计思想，能用「报名系统」类比解释 Action 与 Filter 的区别
  • 熟练使用 add_action / add_filter / do_action / apply_filters / remove_action，理解参数个数与优先级
  • 记住 10 个高频钩子的触发时机，知道什么代码该挂在哪个钩子上
  • 画出一次请求中插件的加载顺序：must-use → 普通插件 → plugins_loaded → init
  • 能独立写出符合规范的最小插件骨架（插件头 + ABSPATH 守卫 + 一个 init 钩子）
  • 能读懂配套演示插件 wp-academy-demo.php 的加载流程，说清每一行的职责

16.1 插件的本质：一个带「身份证」的 PHP 文件 ​

16.1.1 原理说明 ​

WordPress 对插件的唯一硬性要求极其简单：在 wp-content/plugins/ 目录下放一个 PHP 文件，文件开头有一段规定格式的注释（插件头）。就这么简单。没有强制要求的目录结构，没有强制要求的类，没有配置文件。

当这段头注释存在时，WordPress 后台「插件」页面就会把它列出来，显示名称、描述、版本、作者。点击「启用」后，WordPress 会在数据库 wp_options 表的 active_plugins 选项里记录这个文件的路径；此后每一次请求，WordPress 核心在引导阶段都会 include 这个文件——注意，是原样执行，所以你在文件顶层写的任何代码都会在每次请求时运行。

由此可以推出三个重要结论：

  1. 插件的「安装」只是文件就位：把文件放进 wp-content/plugins/ 就装好了，连数据库都不需要动（FTP 上传安装正是利用这一点，见第 17 章）。
  2. 「启用」不等于「运行一次」：启用后插件代码在每次请求都执行，所以插件里绝不能有「只跑一次」的假设。
  3. 插件可以扩展一切，也可以摧毁一切：插件与核心跑在同一个 PHP 进程里，权限等同核心。一个致命语法错误就能让整站 500——这就是为什么第 17 章要专门讲「激活即 500 的救回」。

16.1.2 操作方法：观察一个最小「空插件」 ​

做一个实验，亲手验证上面的结论：

  1. 在练习站的 wp-content/plugins/ 下新建目录 hello-blank/。
  2. 在其中新建 hello-blank.php，内容只写插件头：
php
<?php
/**
 * Plugin Name: 你好，空插件
 * Description:   什么也不做，只为验证「插件的本质是带插件头的 PHP 文件」。
 * Version:       1.0.0
 * Author:        你的名字
 */

// 直接访问保护：ABSPATH 常量只有 WordPress 核心加载时才存在。
defined( 'ABSPATH' ) || exit;
  1. 进入后台「插件 → 已安装的插件」，你会看到「你好，空插件」出现在列表里，名称、描述、版本、作者全部来自头注释。
  2. 点击「启用」，站点一切如常——因为这个文件确实什么逻辑也没有。

图 16-1：只有头注释的文件已被 WordPress 识别为合法插件，可正常启用停用。

💡 插件头的完整字段还包括 Requires at least（最低 WordPress 版本）、Requires PHP（最低 PHP 版本）、Text Domain（国际化）等。上传官方库的插件必须带 License。配套演示插件 wp-academy-demo.php 的开头就是一份标准范例。

16.1.3 常见问题 ​

问：插件文件名有要求吗？ 主文件名习惯与目录同名（如 wp-academy-demo/wp-academy-demo.php），不是强制但强烈建议遵守——WP-CLI、代码扫描工具都按这个约定猜主文件。头注释必须在主文件里，写在其他文件里不会被读取。

问：启用插件时白屏，后台也进不去？ 这是「激活即 500」，FTP 把插件目录改名即可让 WordPress 自动停用它。完整救回流程见第 17 章 17.7 节。

16.2 钩子系统：插件与核心对话的唯一正规渠道 ​

16.2.1 原理说明：为什么要发明「钩子」 ​

插件需要修改 WordPress 的行为：在文章后面加一段版权信息、在保存文章时发一封通知、把登录页换掉……但 WordPress 不允许插件直接改核心文件——一改，下次升级就被覆盖，而且几十个插件各改一份核心，代码立刻变成无法维护的浆糊。

WordPress 的解法是钩子（Hook）：核心代码在上千个关键位置预先埋下「挂载点」，插件把函数「挂」上去，核心执行到挂载点时依次调用所有挂载的函数。核心永远不被修改，扩展能力却是无限的。

用一个生活类比把钩子一次讲透——小区的「报名系统」：

  • 物业（WordPress 核心）公告栏写着：「本周六晚 7 点，广场放电影」——这就是一个挂载点。
  • Action（动作钩子）= 报名参加活动：你登记「放电影时我去摆摊卖爆米花」，邻居登记「放电影时我发传单」。到点了，物业按名单挨个通知，你们各自干各自的事，谁也不干涉谁。登记时可以选「优先级」——号码小的人先行动（比如先占位置）。
  • Filter（过滤器钩子）= 改公告内容：物业规定「任何人都可以在公告贴出前修改一句话，但必须把改后的完整公告交回来」。你把「电影」划掉改成「球赛」，交给下一个人；下一个人把「周六」改成「周日」再交回。最终贴出的是所有人改过的结果。规则只有一条：拿到什么类型，必须交回什么类型，敢把公告纸撕了（不 return）或者交回一张购物小票（return 了错误类型），后面所有人连同最终展示全部遭殃。

这两套机制就是 WordPress 全部扩展性的地基：主题、插件、甚至核心自身的很多功能（比如自动给段落加 <p> 标签）都是挂钩子实现的。

16.2.2 Action：在指定时机执行代码 ​

核心在关键时机调用 do_action( '钩子名', ...参数 )，插件用 add_action() 登记回调：

php
<?php
/**
 * 在文章内容之后追加版权信息（Action 示例）。
 */

// 把 wpa_footer_note() 挂到 wp_footer 动作上，优先级 10（默认）。
add_action( 'wp_footer', 'wpa_footer_note', 10 );

/**
 * 页脚输出版权信息。
 *
 * @return void
 */
function wpa_footer_note() {
	// 仅在前台文章页输出，避免污染其他页面。
	if ( ! is_singular( 'post' ) ) {
		return;
	}

	echo '<p class="wpa-copyright">本文首发于我的练习站，转载请注明出处。</p>';
}

add_action() 的四个参数必须吃透：

参数含义默认值
$hook_name钩子名，区分大小写，写错一个字就静默失效（不报错、不执行）必填
$callback回调：函数名字符串、[对象, '方法']、[类名, '静态方法']、闭包均可必填
$priority优先级，整数，小的先执行；同优先级按登记顺序10
$accepted_args回调接收几个参数（核心 do_action 传了几个，你声明要几个）1

卸载用 remove_action( '钩子名', '回调', 优先级 )——三个参数必须与当初 add_action 完全一致才卸得掉，这是排查优先级冲突的关键工具。

16.2.3 Filter：拿到一个值，改完必须交还 ​

核心在输出或保存某个值之前调用 apply_filters( '钩子名', $值, ...附加参数 )，插件用 add_filter() 登记，回调必须 return 处理后的值：

php
<?php
/**
 * 给文章标题追加「【热】」标记（Filter 示例）。
 *
 * @param string $title 原标题（由核心传入）。
 * @return string 处理后的标题——Filter 回调必须 return。
 */
function wpa_mark_hot_title( $title ) {
	// 只在后台列表外的文章主循环里处理，避免影响菜单等处。
	if ( is_admin() || ! in_the_loop() ) {
		return $title; // 不处理也要原样交还！
	}

	if ( 'Y' === get_post_meta( get_the_ID(), 'is_hot', true ) ) {
		$title = '【热】' . $title;
	}

	return $title;
}

// 声明接收 1 个参数（默认值 1，此处显式写出便于阅读）。
add_filter( 'the_title', 'wpa_mark_hot_title', 10, 1 );

Filter 的铁律，每一条都对应无数真实事故：

  1. 必须 return：忘了 return 等于把值改成 null，后面的过滤器和最终输出全部拿到空值——标题集体消失十有八九是这个原因。
  2. return 的类型必须一致：拿到字符串就还字符串，拿到数组就还数组。
  3. 不修改的分支也要 return 原值：if 里处理了，else 没 return，等于一半情况返回 null。

add_filter 与 add_action 的参数签名完全相同——事实上在核心源码里 add_filter() 和 add_action() 是同一个底层函数的两次包装，区别只在于约定：Action 回调做事、不返回值；Filter 回调改值、必须交还。

16.2.4 回调参数传递：以 save_post 为例 ​

很多钩子会传递多个参数，回调能接到几个，取决于 add_action 的第四个参数 $accepted_args。以 save_post 为例，核心源码中它这样触发：

php
// 核心源码中的触发方式（简化）。
do_action( 'save_post', $post_id, $post, $update );

三个参数分别是：文章 ID、文章对象、是否为更新（true）还是新建（false）。如果你只写 add_action( 'save_post', 'my_cb' )，回调默认只能接到第一个参数 $post_id；要接全部三个，必须显式声明：

php
<?php
/**
 * 文章保存时记录日志（演示多参数回调）。
 *
 * @param int     $post_id 文章 ID。
 * @param WP_Post $post    文章对象。
 * @param bool    $update  是否为更新操作。
 * @return void
 */
function wpa_log_save( $post_id, $post, $update ) {
	// 跳过自动保存与修订版本，只响应人工保存。
	if ( defined( 'DOING_AUTOSAVE' ) && DOING_AUTOSAVE ) {
		return;
	}
	if ( wp_is_post_revision( $post_id ) ) {
		return;
	}

	$action = $update ? '更新' : '新建';
	error_log( sprintf( '[保存日志] %s了文章 #%d（%s）', $action, $post_id, $post->post_title ) );
}

// 优先级 10，接收 3 个参数。
add_action( 'save_post', 'wpa_log_save', 10, 3 );

这个例子还演示了两个工程惯例：跳过自动保存（浏览器每 15 秒会自动存一次草稿，不跳过会被刷屏）、跳过修订版本（每次保存都会同时写一条修订记录，同样会触发 save_post）。

16.2.5 高频钩子速查表 ​

写插件 80% 的时间只跟这张表里的钩子打交道（其余去查官方 Hook Reference）：

钩子类型触发时机典型用途
plugins_loadedAction所有已启用插件文件加载完毕插件初始化、实例化功能类
initAction核心与主题 functions.php 全部就绪注册 CPT、分类法、短代码的指定位置
wp_enqueue_scriptsAction前台准备输出 CSS/JS入队前台样式脚本（唯一正确位置）
admin_enqueue_scriptsAction后台准备输出 CSS/JS入队后台样式脚本
admin_menuAction后台菜单构建时添加/修改后台菜单页、设置页
widgets_initAction小工具系统初始化register_widget() 注册小工具
save_postAction文章保存（新建/更新都触发）保存自定义字段、触发通知；回调收 $post_id
the_contentFilter文章内容输出前追加内容、替换占位符；回调收 HTML 字符串
the_titleFilter文章标题输出前修饰标题；注意菜单、小工具也会过它

⚠️ 时机的因果要记牢：init 之前，文章类型、当前用户等很多 API 还没准备好；所以「注册 CPT」必须挂 init 而不是写在插件顶层。配套演示插件的主文件注释里专门强调了这条（16.5 节精读）。

16.2.6 常见问题 ​

问：钩子名拼错了会怎样？静默失效。add_action( 'innt', ... ) 不会报任何错，只是回调永远不执行。这是插件开发第一大坑。排查顺序：① 对照官方文档逐字符核对钩子名；② 在回调第一行写 error_log( '钩子已触发' );（配合第 05 章或第 30 章讲的 WP_DEBUG_LOG）确认到底执行没有。

问：为什么短代码回调里直接 echo 会错位？ 短代码本质是挂在内容处理流程上的 Filter 型回调，必须 return 字符串，不能 echo。直接 echo 的内容会在 PHP 输出缓冲阶段就写到页面顶部，导致短代码输出「飞」到正文前面。正确写法是拼接字符串返回，输出多时用 ob_start() / ob_get_clean() 包裹。

问：两个插件在同一钩子上打架怎么办？ 先确认各自的优先级参数：数字小的先跑。想让自己最后执行，挂一个足够大的数，如 add_filter( 'the_content', 'my_cb', 999 )。要彻底挤掉对方，用 remove_action() 卸载对方回调——但必须拿到对方登记的完全相同的回调标识与优先级，类方法回调尤其难拿（需要拿到对方的实例），所以优先考虑换优先级而不是卸载。

16.3 插件加载顺序：一次请求的时间线 ​

16.3.1 原理说明 ​

理解加载顺序，才能回答「我的代码此刻能用什么函数」。一次典型请求的关键节点如下：

mermaid
flowchart TD
    A[请求到达 index.php] --> B[加载 wp-config.php<br/>数据库凭据/表前缀/常量]
    B --> C[加载核心函数库<br/>此时插件 API 已可用]
    C --> D[加载 wp-content/mu-plugins/<br/>must-use 插件，自动启用、不可后台停用]
    D --> E[触发 muplugins_loaded]
    E --> F[按 active_plugins 列表<br/>逐个 include 普通插件文件]
    F --> G[触发 plugins_loaded<br/>所有插件已就位]
    G --> H[加载当前主题 functions.php]
    H --> I[触发 init<br/>一切就绪，注册 CPT/分类法在此时]
    I --> J[解析 URL、查询主循环、加载模板]
    J --> K[模板中触发 wp_head/the_content/wp_footer 等]

要点解读：

  • must-use 插件（wp-content/mu-plugins/ 目录下的单文件）最先加载，无需也无法在后台启用停用，常用于必须生效的安全加固或托管商注入代码。
  • 普通插件按启用顺序逐个 include：插件文件顶层的代码（常量定义、类加载、add_action 登记）此刻执行。注意此刻 init 还没触发，所以顶层只能做「登记」，不能做「业务」。
  • plugins_loaded 是所有插件都加载完的信号：需要调用别的插件提供的函数时，挂这里最安全。
  • init 是业务注册的正式舞台：CPT、分类法、短代码、重写规则都挂在这里。主题 functions.php 已先于 init 加载，所以插件在 init 里可以感知主题。
  • 插件之间不能假设对方已加载：A 插件顶层调用 B 插件的函数是不安全的（加载顺序不定），正确做法是双方都挂 plugins_loaded。

16.3.2 操作方法：亲手验证加载顺序 ​

在 16.1 的空插件里加几行日志代码，观察触发顺序：

php
<?php
// 顶层：文件被 include 时立即执行。
error_log( '[顺序实验] 1. 插件文件被加载' );

add_action(
	'plugins_loaded',
	function () {
		error_log( '[顺序实验] 2. plugins_loaded 触发' );
	}
);

add_action(
	'init',
	function () {
		error_log( '[顺序实验] 3. init 触发' );
	}
);

add_action(
	'wp_footer',
	function () {
		error_log( '[顺序实验] 4. wp_footer 触发（前台页面）' );
	}
);

确保 wp-config.php 里调试日志已开启（WP_DEBUG + WP_DEBUG_LOG，见第 3 章），刷新一次前台页面，然后查看 wp-content/debug.log，你会看到严格的 1→2→3→4 顺序。

图 16-2：日志顺序验证了「插件文件加载 → plugins_loaded → init → 模板钩子」的时间线。

实验做完立即删掉这段代码——error_log 留在生产代码里是性能与日志卫生的双重灾难。

16.4 给自己的插件留钩子：可扩展性的元设计 ​

16.4.1 原理说明 ​

既然钩子能让插件扩展核心，那你的插件也可以用同样的方式「留接口」给别人扩展。优秀插件（如 WooCommerce）都提供成百上千个自定义钩子，让第三方不用改它的源码就能扩展功能——这正是 WooCommerce 生态繁荣的技术基础。

方法就是在你的关键位置调用 do_action() / apply_filters()：

php
<?php
// 在你的插件输出内容之前，允许别人改写内容。
$content = apply_filters( 'mfp_card_content', $content, $post_id );

// 在你的插件完成某个操作后，通知别人。
do_action( 'mfp_after_order_created', $order_id, $user_id );

命名约定：插件前缀_事件名，与核心钩子区分开。文档中写清每个钩子的参数与触发时机，你的插件就具备了「被生态扩展」的能力。

16.4.2 常见问题 ​

问：什么时候值得留自定义钩子？ 判断标准：如果某个位置「别人很可能想插入自己的逻辑」（如订单创建后、内容输出前），就留一个。如果只是内部实现细节，不必留——钩子也是公开 API，一旦发布就要维护兼容性。

16.5 精读演示插件：wp-academy-demo.php 加载流程 ​

16.5.1 原理说明 ​

配套插件 ./examples/plugins/wp-academy-demo/ 是本教程的「教具」，它演示了一个组织良好的真实插件：主文件只负责「装配」，六个功能类（CPT、分类法、小工具、短代码、设置、安全）各居其文件。读懂它的启动文件，本章所有概念就全部落地了。

16.5.2 逐段拆解 ​

打开 ./examples/plugins/wp-academy-demo/wp-academy-demo.php，对照下面的脉络读：

  1. 插件头（第 1–47 行）：标准字段齐全——Plugin Name、Description、Version、Requires at least、Requires PHP、Text Domain、License。头注释里还用大段文字记录了「设计决策」与「坑点」，这是值得学习的工程习惯：把「为什么这样写」留在代码旁边。

  2. ABSPATH 守卫（第 49 行）：

php
defined( 'ABSPATH' ) || exit;

ABSPATH 常量只有 WordPress 核心引导时才会定义。如果有人直接在浏览器里访问插件文件 URL（https://站点/wp-content/plugins/wp-academy-demo/wp-academy-demo.php），常量不存在，exit 立即终止，防止文件被脱离上下文执行而泄露信息或触发错误。每一个插件 PHP 文件的第一行可执行代码都应该是它。

  1. 四个常量（第 52–61 行）：WPA_DEMO_VERSION（版本号，入队静态资源时做缓存破坏）、WPA_DEMO_PATH（服务器绝对路径，用于 require）、WPA_DEMO_URL（公开 URL，用于 CSS/JS）、WPA_DEMO_BASENAME（目录/文件名，过滤器用）。用常量而不是散落各处的魔法字符串，是插件可维护性的基本功。

  2. require 六个功能类（第 66–71 行）：主文件只装配，不写业务逻辑；一个类一个文件，命名 class-*.php。

  3. 主类 WPA_Demo 与 init()（第 76–168 行），这是全文件的心脏，注意它如何把本章概念串起来：

php
	public static function init(): void {
		// 翻译文件加载与功能类实例化都放在 plugins_loaded。
		add_action( 'plugins_loaded', [ __CLASS__, 'load_textdomain' ] );
		add_action( 'plugins_loaded', [ __CLASS__, 'load_classes' ] );

		// 小工具必须在 widgets_init 注册，而不是 plugins_loaded。
		add_action( 'widgets_init', [ __CLASS__, 'register_widgets' ] );

		register_activation_hook( __FILE__, [ __CLASS__, 'on_activate' ] );
		register_deactivation_hook( __FILE__, [ __CLASS__, 'on_deactivate' ] );
	}
  • 文件最后一行 WPA_Demo::init() 在插件被 include 时立即执行——但执行的只是登记钩子，真正的实例化推迟到 plugins_loaded，这正是 16.3 节「顶层只登记、不干活」原则的教科书示范。
  • 小工具注册挂 widgets_init 而不是 plugins_loaded：钩子的分工对应 16.2.4 速查表。
  • register_activation_hook / register_deactivation_hook 是两个特殊的「生命周期钩子」，只在启用/停用那一刻执行一次，常用于建表、写入默认选项、刷新固定链接。
  1. 启用钩子的坑（on_activate()，第 142–156 行），头注释里着重警告过：激活请求发生时 init 尚未触发，所以挂在 init 上的 CPT 注册不会自动执行；必须在激活回调里直接调用注册方法，再 flush_rewrite_rules()，否则启用后访问课程归档页会 404。这个「时机错位」是真实插件开发中最高发的 bug 之一。

图 16-3：启用 wp-academy-demo 后，后台左侧出现「课程」菜单，说明 CPT 在 init 上注册成功。

16.5.3 常见问题 ​

问：停用插件会删掉它的数据吗？ 不会。「停用」只把插件从 active_plugins 列表移除并执行停用钩子（演示插件只刷新固定链接）；数据清理是「卸载」的职责，写在 uninstall.php 里（演示插件根目录有范例）。把删数据逻辑挂在停用钩子上是严重设计错误——用户换个主题调试一下，数据就没了。

问：演示插件为什么不用 function 而是一堆类？ 函数式写法在小型插件里完全合法，但类（配合单例模式）能把相关钩子收拢在一个命名空间里，避免全局函数重名——PHP 里两个插件定义同名函数会直接 fatal error。用类 + 方法回调（[ __CLASS__, 'method' ]）天然规避了这个问题。

16.6 动手写一个最小插件骨架 ​

16.6.1 原理说明 ​

把本章知识压缩成一个可复用的骨架。以后写任何插件，都从这个骨架起步：插件头、ABSPATH 守卫、常量、init 钩子、激活/停用钩子，五脏俱全。

16.6.2 完整代码 ​

在 wp-content/plugins/ 下新建 my-first-plugin/my-first-plugin.php：

php
<?php
/**
 * Plugin Name:       我的第一个插件
 * Description:       教学用最小骨架：插件头 + ABSPATH 守卫 + init 钩子 + 生命周期钩子。
 * Version:           1.0.0
 * Requires at least: 6.0
 * Requires PHP:      8.1
 * Author:            你的名字
 * License:           GPL v2 or later
 * Text Domain:       my-first-plugin
 */

// 安全守卫：禁止脱离 WordPress 直接访问本文件。
defined( 'ABSPATH' ) || exit;

// 插件路径与版本常量。
define( 'MFP_VERSION', '1.0.0' );
define( 'MFP_PATH', plugin_dir_path( __FILE__ ) );

/**
 * 插件初始化：挂在 init 上，此刻核心与主题均已就绪。
 *
 * @return void
 */
function mfp_bootstrap() {
	// 业务注册从这里开始，例如：
	// add_shortcode( 'hello', 'mfp_shortcode_hello' );
}
add_action( 'init', 'mfp_bootstrap' );

/**
 * 启用回调：只执行一次，适合写默认选项、刷新重写规则。
 *
 * @return void
 */
function mfp_activate() {
	// 写入默认选项；add_option 已存在时不会覆盖。
	add_option( 'mfp_activated_time', time() );

	// 若注册了 CPT/自定义重写规则，此处刷新固定链接。
	flush_rewrite_rules();
}
register_activation_hook( __FILE__, 'mfp_activate' );

/**
 * 停用回调：只清理运行期状态，绝不删除用户数据。
 *
 * @return void
 */
function mfp_deactivate() {
	flush_rewrite_rules();
}
register_deactivation_hook( __FILE__, 'mfp_deactivate' );

代码规范说明（本教程所有 PHP 代码遵循 WordPress 编码标准 WPCS）：Tab 缩进、Yoda 条件（常量在左，如 'Y' === $flag，防止把比较误写成赋值）、函数名小写下划线并带插件前缀防重名、输出用 esc_html()/esc_attr() 转义、输入用 sanitize_text_field() 等净化——后两条在第 22 章「插件开发入门」会展开细讲。

启用后到后台验证：插件正常激活、无报错；用 WP-CLI 也能验证（预告第 17 章）：

bash
wp plugin activate my-first-plugin
wp option get mfp_activated_time

16.6.3 常见问题 ​

问：骨架里没有 uninstall.php 算完整吗？ 作为「最小可用」算完整；作为「准备发布」不完整。正式发布前应提供 uninstall.php 删除本插件创建的选项与数据（演示插件里有范例），这是对用户数据负责的基本要求。

问：flush_rewrite_rules() 为什么不挂 init 每次执行？ 它会重建全部重写规则并写库，开销极大。官方明确要求只在启用/停用钩子里调用。日常修改固定链接后手动到「设置 → 固定链接」点一次「保存更改」即可（无需真的改内容）。

16.7 插件目录结构最佳实践 ​

16.7.1 原理说明 ​

WordPress 对插件目录结构没有任何强制要求，但社区长期验证的约定已经形成。了解这些约定有助于：① 读别人的插件时快速定位功能；② 自己写插件时避免结构混乱；③ 配合 WP-CLI 与构建工具时路径不出错。

16.7.2 标准目录结构 ​

wp-content/plugins/your-plugin/
├── your-plugin.php          # 主文件（插件头 + ABSPATH 守卫 + 引导代码）
├── uninstall.php            # 卸载时执行（删除数据、清理选项）
├── readme.txt               # 官方库要求（描述、安装说明、FAQ、变更日志）
├── languages/               # 翻译文件（.pot / .po / .mo）
├── includes/                # 功能类与函数库（按功能拆文件）
├── admin/                   # 后台专用代码（设置页、仪表盘小工具）
├── public/                  # 前台专用代码（短代码、小工具）
└── assets/
    ├── css/                 # 前台样式
    └── js/                  # 前台脚本

配套插件 ./examples/plugins/wp-academy-demo/ 就是这套结构的简化版：主文件只装配，includes/ 放六个功能类，assets/css/ 放前台样式，uninstall.php 与 readme.txt 齐全。

16.7.3 常见问题 ​

问：一个插件只有一个 PHP 文件够吗？ 够，但不推荐。功能超过「在页脚加一行版权信息」的插件，都应该拆成多个文件——否则几个月后你自己都看不懂 800 行的单文件。拆分的天然边界就是钩子分工：CPT 注册一个文件、短代码一个文件、设置页一个文件。

本章总结 ​

主题关键结论易错点
