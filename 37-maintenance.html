第 37 章 日常维护清单 ​

🟢 入门难度 ｜ 一句话导览：WordPress 站点不是「装完就万事大吉」的产品，而是需要定期保养的精密机器。本章把运维工作拆解成每日、每周、每月、每季四个节奏，给出可直接照做的清单模板与更新 SOP，让你用最少的时间维持站点健康。

学习目标 ​

  • 能制定适合自己站点的维护节奏表，并理解每项任务的目的
  • 掌握更新管理的完整 SOP：备份 → 测试站验证 → 逐个更新 → 验证
  • 理解 WordPress 维护模式的工作原理，知道何时手动介入
  • 能配置基础的可用性监控与磁盘告警
  • 会使用维护日志模板记录每一次变更，形成可追溯的运维历史
  • 掌握向客户/同事交接站点时的完整文档清单

37.1 维护节奏总表 ​

37.1.1 原理说明 ​

WordPress 维护的核心思想是**「高频小步，低频大步」**。把任务按频率分层，避免「一次性做太多导致顾此失彼」：

  • 每日：确认备份正常、清理垃圾评论。这两项是「保命级」，出问题当天就要发现；
  • 每周：检查更新、测试表单发信。这些是「健康级」，延迟几天通常无大碍，但不能拖到下周；
  • 每月：执行更新、性能抽测、恢复演练抽查、清理闲置用户。这些是「优化级」，需要专门安排时间；
  • 每季：插件清退审计、内容审计、权限复核。这些是「战略级」，涉及架构与合规。

37.1.2 四档频率对照表 ​

频率任务预估耗时工具/方法
每日确认备份任务成功执行1 分钟查看备份日志或插件通知邮件
每日清理垃圾评论（Akismet 拦截后人工复核）2 分钟后台【评论】→ 垃圾评论
每周检查核心/主题/插件更新3 分钟后台【仪表盘 → 更新】

每月执行更新（含测试站验证）30–60 分钟见 37.2 节 SOP

37.1.3 常见问题 ​

Q：小站点也需要这么复杂的清单吗？ 个人博客可以精简到「每周检查更新 + 每月执行更新 + 每月恢复演练抽查」三项。但备份确认无论多小的站都不能省——这是唯一无法事后补救的任务。

Q：有没有自动化工具代替人工检查？ 管理面板类工具（如 ManageWP、MainWP）可以批量监控多个站点的更新与备份状态。但恢复演练和内容审计仍需人工判断，无法完全自动化。

37.2 更新管理 SOP ​

37.2.1 原理说明 ​

WordPress 生态的更新分为三类，风险等级递增：

更新类型频率风险建议策略
核心小版本（7.1.0 → 7.1.1）每月 1–2 次低（安全修复为主）自动更新
核心主版本（7.0 → 7.1）每年 2–3 次中（新功能/API 变更）测试站验证后更新
主题/插件更新不定期中–高（兼容性风险）逐个更新并验证

WordPress 默认开启核心小版本自动更新（安全修复），但主版本和插件/主题更新需要人工触发。这个设计是合理的：安全补丁通常只改几行代码，风险极低；而插件更新可能引入新功能或改变数据库结构。

37.2.2 更新前准备 ​

步骤 1：确认备份可用

在执行任何更新前，必须确认：

bash
# 查看最近一次备份的时间与完整性
cat backups/latest/manifest.txt

如果使用的是 UpdraftPlus 等插件，确认远程存储中有最新备份。

步骤 2：确定更新窗口

选择流量低谷期（通常是凌晨 2–4 点），并预估更新时间：

  • 核心小版本：1–2 分钟；
  • 核心主版本：5–10 分钟（含数据库升级）；
  • 单个插件：1–3 分钟；
  • 主题：1–5 分钟。

37.2.3 执行顺序与验证 ​

标准更新顺序（不可颠倒）：

mermaid
flowchart TD
    A[备份确认] --> B[测试站更新验证]
    B --> C[生产站：更新核心小版本]
    C --> D[验证：首页/后台/关键功能]
    D --> E[更新主题]
    E --> F[验证：前台样式/自定义器]
    F --> G[逐个更新插件]
    G --> H[每更新一个插件，验证一次关键功能]
    H --> I[全部完成，记录维护日志]

为什么必须逐个更新插件？

如果同时更新 5 个插件后站点白屏，你无法确定是哪个插件导致。逐个更新虽然慢，但出问题时的回滚范围最小。

更新后验证清单：

检查项验证方法
首页浏览器访问，确认无白屏/报错
关键文章/页面打开 2–3 篇，确认内容完整
后台登录能正常进入 /wp-admin
联系表单提交一次测试，确认收到邮件
结账页（如有）WooCommerce 走一次完整购买流程
固定链接点击分类/标签页，确认无 404
自定义功能检查主题 functions.php 或自定义插件是否正常

37.2.4 核心自动更新机制 ​

WordPress 的自动更新由 wp-cron 触发，流程如下：

  1. 每天两次检查 wordpress.org 的更新 API；
  2. 发现安全更新后，下载到 wp-content/upgrade/ 临时目录；
  3. 解压、替换文件、运行数据库升级脚本；
  4. 发送通知邮件到管理员邮箱。

控制自动更新的常量（wp-config.php）：

php
// 禁用所有自动更新（不推荐，除非有专业运维流程）
define( 'AUTOMATIC_UPDATER_DISABLED', true );

// 允许核心主版本自动更新（默认仅小版本）
define( 'WP_AUTO_UPDATE_CORE', true );

// 只自动更新小版本（默认行为，无需设置）
define( 'WP_AUTO_UPDATE_CORE', 'minor' );

💡 对于企业站，建议保持默认（仅小版本自动更新），主版本与插件在测试站验证后手动更新。

37.2.5 常见问题 ​

Q：更新后布局错乱怎么办？ 最常见的原因是缓存未清除。按以下顺序清除：

  1. 页面缓存：WP Rocket / W3 Total Cache / LiteSpeed Cache 等插件的「清除缓存」按钮；
  2. CDN 缓存：Cloudflare / 阿里云 CDN 控制台的「刷新缓存」；
  3. 浏览器缓存：强制刷新 Ctrl+Shift+R（Windows）或 Cmd+Shift+R（Mac）；
  4. 对象缓存：wp cache flush（如使用 Redis/Memcached）。

如果清除缓存后仍错乱，检查更新的主题/插件是否引入了新的 CSS/JS 冲突。

Q：更新卡在「正在执行例行维护」页面？ WordPress 在更新时会创建 .maintenance 文件。如果更新超时或中断，该文件可能残留。手动删除：

bash
rm /var/www/html/.maintenance

然后重新执行更新。详见 第 38 章 38.2.9 节。

37.3 维护模式 ​

37.3.1 原理说明 ​

WordPress 的维护模式有两种：

类型触发方式机制影响范围
内置维护模式更新核心/插件/主题时自动触发在根目录创建 .maintenance 文件，WordPress 检测到后显示「正在执行例行维护」全站
插件维护模式手动开启插件通过 wp_die() 或模板重定向显示自定义维护页可配置（仅前台/全站/IP 白名单除外）

内置维护模式的判断逻辑在 wp-includes/load.php 中：

php
// 简化版逻辑
if ( file_exists( ABSPATH . '.maintenance' ) ) {
    // 检查文件创建时间，超过 10 分钟则视为异常残留
    $upgrading = filemtime( ABSPATH . '.maintenance' );
    if ( ( time() - $upgrading ) > 600 ) {
        // 超过 10 分钟，忽略该文件，正常加载
    } else {
        // 显示维护页
        wp_die( '正在执行例行维护，请一分钟后回来。' );
    }
}

关键细节：.maintenance 文件超过 10 分钟会被自动忽略。这是防止更新脚本崩溃后站点永久维护的保险丝。

37.3.2 维护页插件推荐 ​

对于需要长时间维护（如改版、迁移）的场景，内置的「正在执行例行维护」过于简陋。推荐插件：

插件特点适用场景
WP Maintenance Mode免费、支持倒计时、联系表单、SEO 友好（返回 503 状态码）通用
SeedProd付费、拖拽设计器、与邮件营销集成品牌官网
Maintenance轻量、支持自定义背景与文字快速启用

使用 WP Maintenance Mode 的点击级操作：

  1. 安装并激活插件；
  2. 进入【设置 → WP Maintenance Mode】；
  3. 「常规」标签：状态改为「已激活」，选择「仅对未登录用户显示维护页」；
  4. 「设计」标签：上传 Logo、修改标题与描述、设置倒计时；
  5. 「模块」标签：开启「联系表单」与「订阅邮件收集」；
  6. 保存后，用无痕窗口访问前台验证效果。

37.4 安全维护节奏 ​

37.4.1 原理说明 ​

安全维护与 第 32 章 的安全加固形成互补：32 章是「一次性配置」，本章是「周期性复查」。

37.4.2 安全维护任务清单 ​

频率任务方法
每日检查安全插件告警邮件Wordfence / iThemes Security 通知
每周审查登录日志（是否有异常 IP 尝试登录）安全插件的「登录安全」模块
每月执行完整安全扫描Wordfence 扫描 / Sucuri SiteCheck
每月检查文件完整性（核心文件是否被篡改）Wordfence 的「文件比较」功能
每季审查用户权限（是否有不认识的账号）后台【用户】列表
每季检查 API 密钥/密码是否泄露haveibeenpwned.com 查询管理员邮箱

💡 如果安全插件报告「核心文件被修改」，不要立即修复——先确认是 WordPress 自动更新导致的正常变更，还是真正的入侵。对比修改时间与更新日志即可判断。

37.5 监控告警 ​

37.5.1 可用性监控 ​

UptimeRobot（免费版支持 50 个监控项，5 分钟间隔）：

  1. 注册 uptimerobot.com；
  2. 添加监控项：
    • HTTP(s)：监控首页 URL，期望状态码 200；
    • Keyword：监控首页是否包含「WordPress」关键词（防止被黑后页面内容被替换）；
    • Ping：监控服务器 IP；
  3. 配置告警渠道：邮件、Telegram、Slack、Webhook。

国内替代方案：阿里云云监控、腾讯云可观测平台、监控宝。

37.5.2 磁盘与 inode 告警 ​

WordPress 站点的磁盘告警阈值建议：

指标告警阈值检查命令
磁盘使用率≥ 80%df -h
inode 使用率≥ 80%df -i
备份目录增长单周增长 ≥ 50%du -sh backups/ 对比

为什么关注 inode？ uploads 目录的小图片过多会耗尽 inode，即使磁盘空间充足也无法写入新文件。这是 WordPress 站特有的问题。

自动告警脚本示例（加入 crontab 每日执行）：

bash
#!/bin/bash
# 磁盘与 inode 监控脚本
THRESHOLD=80

df -h | awk 'NR>1 {gsub(/%/,"",$5); if ($5 >= '"$THRESHOLD"') print "磁盘告警: " $6 " 使用率 " $5 "%"}'
df -i | awk 'NR>1 {gsub(/%/,"",$5); if ($5 >= '"$THRESHOLD"') print "inode告警: " $6 " 使用率 " $5 "%"}'

37.6.1 维护日志模板 ​

markdown

37.7 常见问题汇总 ​

更新卡住留 .maintenance 文件 ​

现象：访问站点显示「正在执行例行维护，请一分钟后回来」，但等了 10 分钟仍不消失。

原因：更新脚本执行超时（如大插件解压慢、服务器负载高），.maintenance 文件未被正常删除。

解决：

bash
# 手动删除维护文件
rm /var/www/html/.maintenance

# 检查是否有残留的升级临时目录
ls -la /var/www/html/wp-content/upgrade/
# 如有残留，删除后重新更新

更新后布局错乱（清缓存顺序） ​

现象：主题更新后，前台 CSS 错乱，但后台预览正常。

原因：浏览器、CDN、页面缓存插件各自缓存了旧版 CSS/JS。

解决（必须按顺序）：

bash
# 1. 清除页面缓存插件
wp cache flush  # 或插件提供的清除按钮

# 2. 清除 CDN 缓存（Cloudflare 示例）
curl -X POST "https://api.cloudflare.com/client/v4/zones/ZONE_ID/purge_cache" \
  -H "Authorization: Bearer API_TOKEN" \
  -H "Content-Type: application/json" \
  --data '{"purge_everything":true}'

# 3. 清除浏览器缓存：强制刷新或无痕窗口验证

自动更新通知邮件解读 ​

WordPress 发送的自动更新邮件有三种，含义不同：

邮件主题含义是否需要处理
「Your site has been updated to WordPress X.Y.Z」小版本自动更新成功否，仅需确认站点正常
「WordPress X.Y.Z is available」主版本可用，需手动更新是，安排测试站验证
「Some plugins were automatically updated」插件自动更新（如启用了自动更新）是，验证插件功能

💡 如果收到「Update failed」邮件，说明自动更新失败。登录后台手动更新，并检查 wp-content/upgrade/ 目录权限。

37.7.4 维护中的数据库优化 ​

WordPress 数据库在长期使用后会积累冗余数据，每月执行一次优化能保持查询效率：

bash
# 清理文章修订版本（保留最近 3 版）
wp db query "DELETE FROM wp_posts WHERE post_type = 'revision' AND ID NOT IN (
    SELECT * FROM (
        SELECT ID FROM wp_posts WHERE post_type = 'revision'
        ORDER BY post_date DESC LIMIT 3
    ) AS tmp
);"

# 清理自动草稿
wp db query "DELETE FROM wp_posts WHERE post_status = 'auto-draft';"

# 清理回收站
wp db query "DELETE FROM wp_posts WHERE post_status = 'trash';"

# 清理垃圾评论
wp db query "DELETE FROM wp_comments WHERE comment_approved = 'spam';"
wp db query "DELETE FROM wp_comments WHERE comment_approved = 'trash';"

# 优化表（InnoDB 主要是重建索引）
wp db optimize

37.7.6 维护中的内容健康检查 ​

每月执行一次内容健康检查，确保站点内容质量：

bash
# 检查孤立附件（无父文章的媒体文件）
wp db query "SELECT COUNT(*) FROM wp_posts WHERE post_type = 'attachment' AND post_parent = 0;"

# 检查空标签/分类
wp db query "SELECT t.name FROM wp_terms t
    LEFT JOIN wp_term_taxonomy tt ON t.term_id = tt.term_id
    WHERE tt.count = 0 AND tt.taxonomy IN ('category', 'post_tag');"

# 检查 404 链接（需配合插件如 Broken Link Checker）
# 或使用 WP-CLI 扫描所有内部链接
wp db query "SELECT ID, post_title FROM wp_posts
    WHERE post_content LIKE '%href=\"http%' LIMIT 10;"

内容健康检查的输出结果应记录在维护日志中，作为内容审计的依据。

37.7.7 维护中的插件兼容性矩阵 ​

建立插件兼容性矩阵，避免「插件 A 与插件 B 冲突」的排查困难：

插件版本兼容的 WP 版本已知冲突最后验证日期
WooCommerce8.1.07.0+与某缓存插件的 mini-cart 冲突2026-10-01
Yoast SEO21.07.0+无2026-09-15
WP Rocket3.157.0+与某安全插件的 heartbeat 控制冲突2026-09-20

每次更新插件后，更新矩阵中的「版本」与「最后验证日期」列。如果某插件连续两个版本都与核心功能冲突，考虑寻找替代品。

本章总结 ​

本章将 WordPress 维护工作系统化为「每日/每周/每月/每季」四个节奏，每项任务都有明确的操作路径与耗时预估。更新管理 SOP 强调了「备份 → 测试站验证 → 逐个更新 → 验证」的不可颠倒顺序，以及更新后验证清单的必要性。维护模式、安全复查、监控告警、维护日志与交接文档构成了完整的运维闭环。

维护工作的最高境界是「无事发生」——通过规律的节奏把问题消灭在萌芽状态。下一章将讨论「有事发生」时的应对策略：故障排查与应急恢复。
