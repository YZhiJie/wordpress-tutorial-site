第 34 章 备份策略与工具 ​

🟡 进阶难度 ｜ 一句话导览：备份是网站运维的「保险丝」——没有备份的更新等于赌博，没有验证的备份等于没做。本章从 3-2-1 原则讲起，覆盖插件点击备份、服务器级快照、脚本级自动化三套方案，并逐段精读配套脚本 ./examples/bin/backup.sh。

学习目标 ​

  • 理解 3-2-1 备份原则在 WordPress 场景中的具体含义
  • 能列出「必须备份」与「可以重新下载」的文件清单，缩小备份体积
  • 掌握 UpdraftPlus 插件的完整备份/恢复点击级操作
  • 能读懂并定制 ./examples/bin/backup.sh 脚本，实现宿主机自动化备份
  • 根据站点类型（博客/企业站/电商）制定合理的备份频率
  • 能在本地 Docker 环境完成一次完整的恢复演练

34.1 备份的基本原则 ​

34.1.1 原理说明：为什么备份是底线工程 ​

WordPress 站点由文件与数据库两部分组成，任何一方的损坏都会导致站点不可用：

  • 数据库存储所有内容（文章、页面、评论、设置、用户、小工具配置等），是站点的「大脑」。
  • 文件系统存储程序代码、主题、插件、上传的媒体文件，是站点的「躯体」。

一旦遭遇误操作（更新插件导致白屏）、服务器故障（磁盘损坏）、安全事件（被植入恶意代码）或人为错误（删错数据库），没有备份就意味着数月至数年的内容积累瞬间归零。

3-2-1 备份原则 ​

业界通行的 3-2-1 原则在 WordPress 中的映射如下：

原则含义WordPress 实践
3 份副本数据至少保留 3 份1 份生产环境本身 + 1 份本地/同服务器备份 + 1 份异地/云端备份
2 种介质使用 2 种不同存储介质服务器本地磁盘 + 对象存储（阿里云 OSS / AWS S3 / Google Drive）
1 份异地至少 1 份存放在异地云存储与服务器不在同一可用区，避免火灾/机房级故障

⚠️ 备份不验证等于没备份。很多人把备份文件生成出来就心安理得，直到真正需要恢复时才发现：备份包损坏、SQL 导出不完整、远程存储授权过期导致文件未上传成功。本章会专门安排一节「恢复演练」来破除这一幻觉。

34.1.2 备份范围：什么该备，什么不用备 ​

WordPress 的备份并非「把整个网站目录打包」那么简单。核心文件可以从 wordpress.org 按版本号重新下载，真正需要保护的只有三类数据：

必须备份（不可替代的数据）：

类别具体路径/内容说明
数据库全表mysqldump 导出的 SQL所有内容、设置、用户、评论
上传文件wp-content/uploads/媒体库图片、文档、视频
主题文件wp-content/themes/（含子主题）自定义代码、样式、模板修改
插件文件wp-content/plugins/（含自定义插件）自定义插件代码、配置落盘文件
配置文件wp-config.php数据库凭据、表前缀、盐值、自定义常量

可以不备份（可重新获取）：

类别具体路径说明
WordPress 核心wp-admin/、wp-includes/、根目录 PHP按版本号从官方重新下载
可复装插件免费目录插件可从 wordpress.org 插件库重装
缓存文件wp-content/cache/、wp-content/uploads/cache/可自动重建，体积通常很大

💡 缩小备份体积的关键策略：排除缓存目录、排除日志文件、排除已安装但可随时重装的免费插件（商业插件需保留授权文件）。

图 34-1：深绿色为必须备份区域，浅绿色为建议备份区域，灰色为可重新下载或重建的区域。

34.1.3 备份类型对比：完整、增量、差异 ​

维度完整备份增量备份差异备份
定义每次备份全部选定数据只备份自上次备份后变化的数据只备份自上次完整备份后变化的数据
备份速度慢（数据量大）最快（仅增量）中等（逐次累积）
恢复速度最快（单包恢复）最慢（需链式恢复：完整+所有增量）中等（完整+最新差异）
存储占用最大最小中等
适用场景小型站点、数据库大型媒体站、每日变更极多的场景中等规模站点、每周一次的中间方案
WP 实践数据库导出天然是完整备份rsync --link-dest 可实现文件增量周日晚间完整+每日差异

对于绝大多数 WordPress 站点，推荐采用「数据库每日完整备份 + 文件每周完整备份 + uploads 目录增量同步到对象存储」的混合策略。数据库体积通常只有几十到几百 MB，每日完整导出不会带来存储压力；而 uploads 目录可能达到数十 GB，适合用增量工具（如 rclone 同步到 OSS/S3）。

34.2 方案一：插件级备份（UpdraftPlus） ​

34.2.1 原理说明 ​

插件级备份是最适合非技术用户的方案。UpdraftPlus 是 WordPress 官方插件库中安装量最高的备份插件（超过 300 万活跃安装），其核心原理是：

  1. 通过 PHP 的 mysqldump 封装或逐表 SELECT 方式导出数据库；
  2. 使用 PHP 的 ZipArchive 或系统 zip 命令打包文件；
  3. 通过各云存储的 SDK 或 OAuth 授权上传到远程；
  4. 提供一键恢复界面，自动解包+导入 SQL+匹配文件。

34.2.2 点击级操作：安装到恢复全流程 ​

步骤 1：安装与激活

进入后台【插件 → 安装插件】，搜索「UpdraftPlus」，安装并激活「UpdraftPlus WordPress Backup Plugin」。

图 34-2：UpdraftPlus 设置面板，可在此配置备份计划、远程存储与手动触发备份。

步骤 2：设置备份计划

进入【设置 → UpdraftPlus Backups】：

  1. 文件备份计划：建议设为「每周」（文件变化频率低于数据库）。
  2. 数据库备份计划：建议设为「每日」（内容更新通常发生在数据库层）。
  3. 保留数量：建议至少保留 7 份数据库 + 4 份文件，视远程存储容量调整。

步骤 3：配置远程存储

在「选择远程存储」区域勾选目标：

  • Google Drive：点击授权按钮，按 OAuth 流程登录 Google 账号并允许权限；
  • 阿里云 OSS：选择 S3-Compatible，填写 Endpoint、AccessKey、Bucket；
  • 腾讯云 COS：同样选择 S3-Compatible 模式；
  • FTP/SFTP：适用于自有服务器或 NAS。

⚠️ 远程存储授权令牌会过期（尤其是 OAuth 2.0 类）。建议每季度检查一次「测试存储」按钮，确保备份确实能上传成功。

步骤 4：手动执行一次完整备份

点击「立即备份」按钮，在弹窗中勾选：

  • [x] 备份数据库
  • [x] 备份插件
  • [x] 备份主题
  • [x] 备份上传文件
  • [x] 备份其他内容（wp-config.php 等落在此项）
  • [x] 备份到远程存储

备份过程可能需要 1–10 分钟，取决于站点体积。完成后在「现有备份」标签页能看到时间戳条目。

步骤 5：恢复演练

在同一页面的「现有备份」列表中，点击某个备份条目的「恢复」按钮：

  1. 选择要恢复的组件（数据库、插件、主题、上传、其他）；
  2. UpdraftPlus 会先下载备份包到本地临时目录；
  3. 自动解压并导入数据库；
  4. 恢复完成后提示「成功」，此时应检查前台与后台是否正常。

💡 强烈建议在做任何恢复演练前，先用 UpdraftPlus 的「克隆/迁移」功能或手动再备份一次当前状态，防止「恢复了一个旧备份，丢失了今天的新数据」。

34.2.3 常见问题 ​

Q：UpdraftPlus 免费版够用吗？ 免费版已支持定时备份、远程存储（Google Drive/OneDrive/Dropbox/FTP/S3 等）与一键恢复。付费版主要增加增量备份、多站点支持、自动迁移、更细粒度的排除规则。对于个人博客和中小型企业站，免费版完全足够。

Q：备份包巨大，远程存储空间不够怎么办？ 在「设置 → 排除文件」中排除大体积目录：

  • wp-content/uploads/ 下的 .mp4、.mov 视频文件（媒体文件建议单独走对象存储 CDN，不纳入备份包）；
  • wp-content/cache/ 缓存目录；
  • 日志目录如 wp-content/debug.log。

Q：恢复后前台白屏怎么办？ 最常见的原因是新旧环境 PHP 版本不一致。UpdraftPlus 恢复的是数据而非运行环境。如果备份来自 PHP 7.4 的站点，恢复到 PHP 8.3 环境时，某些旧主题/插件可能触发致命错误。解决方式见 第 38 章 38.2.1 节。

34.3 方案二：服务器级备份 ​

34.3.1 原理说明 ​

服务器级备份不依赖 WordPress 插件，而是由操作系统或虚拟化层完成，适合有服务器管理权限的用户。其优势是备份过程对 PHP 运行时零侵入，即使 WordPress 已白屏也能正常执行。

34.3.2 面板快照（可视化操作） ​

如果你使用宝塔面板、cPanel、Plesk 或云厂商控制台：

面板/平台快照类型操作路径
宝塔面板网站备份 + 数据库备份【网站 → 对应站点 → 备份】
阿里云 ECS磁盘快照控制台 → 云服务器 ECS → 本实例磁盘 → 创建快照
腾讯云 CVM云硬盘快照控制台 → 云硬盘 → 创建快照
AWS EC2EBS SnapshotEC2 控制台 → Elastic Block Store → Snapshots

磁盘快照的优点是块级一致、恢复极快（分钟级回滚）。缺点是：

  • 通常与服务器同地域，不满足 3-2-1 的「异地」要求；
  • 快照本身不可直接读取（无法单独提取某个 SQL 文件或某个主题文件）；
  • 按量计费，长期保留多份快照成本较高。

因此，磁盘快照适合作为「灾难恢复的最后一道防线」，日常仍需配合逻辑备份（SQL + 文件打包）使用。

34.3.3 rsync 文件同步（命令行操作） ​

rsync 是 Linux 下的增量同步利器，适合把 uploads 目录实时或定时同步到另一台服务器或 NAS：

bash
# 每日凌晨 2 点将 uploads 增量同步到备份服务器
# --delete：删除备份端已不存在于源端的文件，保持两侧一致
# -avz：归档模式+详细输出+压缩传输
0 2 * * * rsync -avz --delete \
  /var/www/html/wp-content/uploads/ \
  backup-user@backup-server:/backups/wp-uploads/

对于数据库，rsync 无能为力（MySQL 数据文件在运行中直接复制会损坏），必须走 mysqldump 或 WP-CLI 导出。

34.4 方案三：脚本级自动化（逐段精读 backup.sh） ​

34.4.1 原理说明 ​

脚本级备份是开发者和运维人员最可控的方案。它将备份流程固化为 Bash 脚本，配合 cron 定时执行，输出标准化的备份包与清单文件。本章配套的 ./examples/bin/backup.sh 就是一个生产可用的示例，下面逐段精读。

34.4.2 脚本逐段精读 ​

打开 ./examples/bin/backup.sh，整体结构如下：

  1. 文件头与说明：用途、输出三件套（database.sql.gz / content.tar.gz / manifest.txt）、坑点提示；
  2. 安全选项：set -euo pipefail；
  3. 路径定位：不依赖调用者当前目录；
  4. 参数配置：BACKUP_DIR、KEEP_DAYS、TIMESTAMP；
  5. 容器检查：确保 db 与 wordpress 容器在运行；
  6. 数据库导出：WP-CLI wp db export 管道给 gzip；
  7. 文件打包：tar 打包 themes / plugins / uploads，排除缓存；
  8. 清单生成：manifest.txt 记录 URL、版本、sha256、文件大小；
  9. 过期清理：find -mtime 删除超期备份。

第一段：安全选项与路径定位 ​

bash
set -euo pipefail
  • -e：任何命令返回非 0 即退出，防止「前面失败、后面继续」的级联错误；
  • -u：使用未定义变量时报错，防止拼写错误导致空值；
  • -o pipefail：管道中任一命令失败，整个管道返回非 0。这是备份脚本的关键——如果 wp db export 失败但 gzip 成功，没有 pipefail 的话脚本会误判为成功。
bash
SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
PROJECT_DIR="$(cd "$SCRIPT_DIR/.." && pwd)"
cd "$PROJECT_DIR"

这三行保证无论从哪里调用脚本，都能正确定位到项目根目录。bin/backup.sh 的上一级就是 compose 项目目录，后续所有相对路径都基于此。

第二段：参数与目录 ​

bash
BACKUP_DIR="${BACKUP_DIR:-$PROJECT_DIR/backups}"
KEEP_DAYS="${KEEP_DAYS:-14}"

使用 ${VAR:-default} 语法，允许通过环境变量覆盖默认值：

bash
# 示例：把备份写到挂载的 NFS 目录，保留 30 天
BACKUP_DIR=/mnt/nfs/wp-backups KEEP_DAYS=30 ./bin/backup.sh

第三段：容器检查 ​

bash
docker compose up -d db wordpress >/dev/null

脚本不假设容器已在运行。如果用户手动停掉了容器，up -d 会静默拉起；如果已在运行，则无操作。这保证脚本在 cron 中也能可靠执行。

第四段：数据库导出 ​

bash
docker compose run --rm -T cli wp db export - \
    | gzip -c -9 > "$DEST/database.sql.gz"
  • run --rm -T：启动一次性 cli 容器，执行完自动删除；-T 禁用伪终端，避免管道中的控制字符问题；
  • wp db export -：- 表示输出到标准输出（而非文件），这样可以直接管道给 gzip；
  • gzip -c -9：-c 输出到标准输出，-9 最大压缩率。数据库 SQL 文本压缩率通常能达到 70%–90%。

💡 为什么不直接用 mysqldump？因为 WP-CLI 会自动读取 wp-config.php 中的数据库凭据，无需在脚本里硬编码密码，更安全、更便携。

第五段：文件打包 ​

bash
docker compose exec -T wordpress tar \
    -czf - \
    -C /var/www/html \
    --exclude='wp-content/cache' \
    --exclude='wp-content/themes/*/cache' \
    --exclude='wp-content/plugins/*/cache' \
    --exclude='*/cache/*' \
    wp-content/themes \
    wp-content/plugins \
    wp-content/uploads \
    > "$DEST/content.tar.gz"
  • -C /var/www/html：先切换工作目录，这样打包出来的归档内部路径是相对 wp-content/ 的，恢复时直接解压到 WordPress 根目录即可；
  • --exclude：多级排除缓存目录，防止把可重建的缓存文件打包进来浪费空间；
  • exec -T：在已运行的 wordpress 容器内执行，避免启动新容器的开销。

第六段：清单生成 ​

bash
SITE_URL="$(docker compose run --rm -T cli wp option get siteurl 2>/dev/null || echo 'unknown')"
WP_VERSION="$(docker compose run --rm -T cli wp core version 2>/dev/null || echo 'unknown')"

清单文件是恢复时的「身份证」：它告诉你这份备份来自哪个站点、什么版本、何时生成。

bash
if command -v sha256sum >/dev/null 2>&1; then
    ( cd "$DEST" && sha256sum database.sql.gz content.tar.gz )
elif command -v shasum >/dev/null 2>&1; then
    ( cd "$DEST" && shasum -a 256 database.sql.gz content.tar.gz )

跨平台兼容：Linux 通常有 sha256sum，macOS 只有 shasum，脚本对两者都做了适配。

第七段：过期清理 ​

bash
DELETED="$(find "$BACKUP_DIR" -mindepth 1 -maxdepth 1 -type d -mtime "+$KEEP_DAYS" -print -exec rm -rf {} + || true)"
  • -mindepth 1 -maxdepth 1：只在备份根目录的第一层查找时间戳目录，防止误删子目录或备份根目录本身；
  • -mtime +$KEEP_DAYS：修改时间超过 KEEP_DAYS 天的目录；
  • -print -exec rm -rf {} +：先打印被删目录名，再执行删除；
  • || true：即使没有过期备份，find 返回空也不是错误，保证脚本不中断。

34.4.3 将脚本加入定时任务 ​

bash
# 编辑当前用户的 crontab
crontab -e

# 每日凌晨 3 点执行备份，输出日志到 backups/backup.log
0 3 * * * cd /path/to/wordpress-tutorial && ./bin/backup.sh >> backups/backup.log 2>&1

建议同时配置 logrotate 防止日志文件无限增长：

bash
# /etc/logrotate.d/wp-academy-backup
/path/to/wordpress-tutorial/backups/backup.log {
    daily
    rotate 14
    compress
    missingok
    notifempty
}

34.5 备份频率决策表 ​

不同站点类型的数据变化频率与业务重要性不同，备份策略也应差异化：

站点类型数据库频率文件频率保留周期额外建议
个人博客（日更）每日每周30 天发长文前手动触发一次
企业官网（周更）每周每周90 天发版前必须手动备份
电商站（WooCommerce）每日或每 6 小时每日90 天订单即数据库，必须实时或准实时
会员/社区站每日每周60 天用户数据变化快，考虑主从复制
开发/测试站重大变更前重大变更前7 天用快照快速回滚

💡 黄金法则：「恢复点目标（RPO）」——你能接受丢失多长时间的数据？电商站答案是「5 分钟」，博客可以是「24 小时」。RPO 决定了你的备份频率。

34.6 恢复演练 SOP ​

34.6.1 原理说明 ​

备份的价值不在「存」，而在「能恢复」。恢复演练应在隔离环境中进行，绝不要直接在生产站上「试恢复」。本章使用教程配套的 Docker 环境作为演练场。

34.6.2 本地 Docker 恢复操作 ​

前提：已按 第 02 章 搭建好 Docker Compose 环境，且 ./examples/bin/backup.sh 已生成至少一份备份。

步骤 1：准备干净的 WordPress 容器

bash
# 进入配套示例目录
cd wordpress-tutorial/examples

# 仅删除 WordPress 容器与卷（保留备份目录），然后重新创建
docker compose down -v
docker compose up -d db wordpress

步骤 2：解压文件备份

bash
# 假设最新备份在 backups/20261004-030000/
BACKUP="backups/20261004-030000"

# 将 content.tar.gz 解压到 WordPress 容器内的 /var/www/html
# 注意：要在宿主机执行，通过 docker cp 或挂载卷方式传入
docker compose exec wordpress tar -xzf - -C /var/www/html < "$BACKUP/content.tar.gz"

步骤 3：导入数据库

bash
# 先解压 gzip，再通过 WP-CLI 导入
gunzip -c "$BACKUP/database.sql.gz" > /tmp/restore.sql
docker compose run --rm cli wp db import /tmp/restore.sql

💡 如果导入时出现 ERROR 1062 重复键错误，说明新容器已运行过安装向导、产生了初始数据。此时应先 wp db reset --yes 清空数据库再导入。

步骤 4：验证恢复结果

打开 http://localhost:8080 检查：

  1. 首页是否正常加载；
  2. 文章/页面内容是否完整；
  3. 媒体库图片是否能正常显示；
  4. 后台 http://localhost:8080/wp-admin 能否登录；
  5. 固定链接是否正常（必要时进后台【设置 → 固定链接】点「保存更改」刷新重写规则）。

图 34-3：恢复后必须逐项验证的六个检查点，任何一项失败都说明备份或恢复过程存在问题。

34.6.3 常见问题 ​

Q：恢复后图片 404 怎么办？ 如果备份来自 http://localhost:8080 以外的站点，恢复后数据库中的图片 URL 仍指向旧地址。需要使用 WP-CLI search-replace 替换域名，具体操作见 第 35 章。

Q：恢复后提示「数据库连接错误」？ 检查 wp-config.php 中的数据库凭据是否与当前 Docker 环境的 .env 配置一致。Docker 环境中数据库主机通常是 db:3306，而生产环境可能是 localhost 或云数据库地址。

Q：恢复后主题设置丢失？ 如果备份的是 wp-content 但数据库来自另一时间点，主题设置（存在 wp_options 表中）与主题文件版本不匹配。确保数据库与文件备份来自同一时间点。

34.7 常见问题汇总 ​

备份包巨大如何处理 ​

uploads 目录是备份体积膨胀的首要元凶。排查方法：

bash
# 查看 uploads 各子目录大小
du -sh wp-content/uploads/* | sort -rh | head -20

常见大体积来源与对策：

来源对策
原始视频文件（.mp4/.mov）视频走对象存储/CDN，本地只存缩略图；备份时排除
未压缩的原始图片先用 第 30 章 的插件压缩
备份插件自身遗留的旧备份包定期清理 wp-content/updraft/ 或对应插件目录
日志文件排除 debug.log、error_log

恢复后白屏（PHP 版本差异） ​

现象：恢复后前台或后台白屏，开启 WP_DEBUG 后看到类似 Fatal error: Uncaught Error: Call to undefined function...。

原因：备份源站的 PHP 版本与恢复目标环境的 PHP 版本差异过大（如 PHP 7.4 → 8.3），旧主题/插件使用了已废弃的函数或语法。

解决：

  1. 临时切换目标环境到与源站相同的 PHP 版本，恢复成功后再逐步升级；
  2. 或在恢复前先在测试环境将主题/插件更新到兼容新版本；
  3. 参考 第 38 章 的白屏排查流程。

远程存储授权过期 ​

现象：备份脚本执行成功，但远程存储里没有新文件；或 UpdraftPlus 日志显示「401 Unauthorized」。

原因：Google Drive / Dropbox 的 OAuth 2.0 访问令牌有效期通常为 1 小时，刷新令牌可能因用户改密码或撤销授权而失效。

解决：

  1. 进入 UpdraftPlus 设置，点击「重新认证」或「测试存储」；
  2. 对于 S3-Compatible（OSS/COS），检查 AccessKey 是否被轮换；
  3. 脚本级备份应定期检查 backup.log 中的上传结果。

本章总结 ​

本章从备份的 3-2-1 原则出发，明确了 WordPress 备份的核心范围（数据库 + wp-content 的 themes/plugins/uploads + wp-config.php），对比了完整/增量/差异三种备份类型。随后介绍了三套实操方案：

  1. UpdraftPlus 插件：适合非技术用户，点击级完成定时备份、远程存储与恢复；
  2. 服务器级：面板快照与 rsync，适合有服务器权限的运维人员；
  3. 脚本级：逐段精读了 ./examples/bin/backup.sh，理解其容器化备份、清单生成与过期清理机制。

最后强调了「备份不验证等于没备份」——在本地 Docker 环境完成一次恢复演练，是检验备份有效性的唯一标准。第 35 章将在此基础上，讲解如何把备份用于站点迁移。
