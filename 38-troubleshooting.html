第 38 章 故障排查与应急恢复 ​

🔴 高级难度 ｜ 一句话导览：故障排查不是「重启试试」的玄学，而是「复现 → 分层定位 → 二分缩小 → 最小修复」的科学流程。本章先给你一张日志地图，再逐个击破 10 类高频故障，最后用备份完成一次完整的应急恢复演练。

学习目标 ​

  • 掌握「复现 → 分层定位 → 二分停用 → 最小复现」的排查方法论
  • 能根据故障类型快速定位到对应的日志文件（PHP error_log、WP debug.log、Nginx/Apache、MySQL、Docker）
  • 掌握 10 类高频故障的排查步骤与修复方法
  • 能使用 ./examples/bin/backup.sh 的备份完成完整的应急恢复
  • 掌握「求助前自检清单」，能向他人清晰描述问题
  • 建立全教程故障索引表，实现「症状 → 章节」的快速跳转

38.1 排查方法论 ​

38.1.1 原理说明 ​

WordPress 故障的本质是**「请求生命周期中的某一环断裂」**。一个 HTTP 请求从浏览器到数据库要经过：

浏览器 → DNS → CDN → Web 服务器(Nginx/Apache) → PHP-FPM → WordPress 核心 → 主题/插件 → 数据库

每一环都可能出问题。排查的核心原则是：

  1. 先复现，再动手：确保你能稳定触发问题，而不是「偶尔出现」；
  2. 分层定位：从最外层（浏览器）向最内层（数据库）逐层排查；
  3. 二分缩小：通过停用一半插件/切换默认主题，把问题范围减半；
  4. 最小复现：创建一个只包含问题核心的测试环境，排除干扰。

38.1.2 排查流程图 ​

mermaid
flowchart TD
    A[用户报告故障] --> B{能否复现？}
    B -->|否| C[收集更多信息<br/>浏览器/时间/操作步骤]
    B -->|是| D[开启调试模式<br/>WP_DEBUG_LOG]

    F -->|WordPress 层| I[检查 debug.log/插件冲突]
    F -->|数据库层| J[检查 MySQL 错误日志/连接数]

    I --> L[二分停用插件/切换主题]
    L --> M{问题消失？}

38.1.3 排查原则：先查日志，再动手 ​

很多新手的第一反应是「改配置试试」，这是大忌。日志是故障现场的第一手证据，盲目修改会破坏现场。

正确的顺序：

  1. 开启 WP_DEBUG_LOG 收集错误；
  2. 查看 Web 服务器与 PHP 错误日志；
  3. 根据日志中的「Fatal error」「Warning」「Notice」定位文件与行号；
  4. 理解错误含义后，再决定是改配置、更新插件还是回滚。

38.2 日志地图 ​

38.2.1 PHP 错误日志 ​

PHP 层的致命错误（Fatal Error）通常导致白屏或 500 错误。

环境日志路径查看方式
传统 LAMP/LNMP/var/log/php_errors.log 或 php.ini 中 error_log 指定路径tail -f /var/log/php_errors.log
Docker（本教程配套）容器内标准输出docker compose logs wordpress
宝塔面板/www/wwwlogs/php_error.log面板【日志】模块

开启 PHP 错误显示（仅限开发环境）：

php
// wp-config.php
define( 'WP_DEBUG', true );
define( 'WP_DEBUG_LOG', true );      // 写入 wp-content/debug.log
define( 'WP_DEBUG_DISPLAY', false ); // 不在页面显示（防止泄露路径）

⚠️ 生产环境必须设置 WP_DEBUG_DISPLAY = false，否则错误信息会暴露服务器路径与数据库凭据。

38.2.2 WordPress debug.log ​

WordPress 的 debug.log 位于 wp-content/debug.log，记录 PHP 错误、数据库查询错误与弃用函数警告。

bash
# 实时查看
tail -f wp-content/debug.log

# 只查看 Fatal Error
grep "Fatal error" wp-content/debug.log | tail -20

38.2.3 Web 服务器日志 ​

Nginx：

bash
# 访问日志（看请求是否到达 Nginx）
tail -f /var/log/nginx/access.log

# 错误日志（看 Nginx 与 PHP-FPM 通信是否异常）
tail -f /var/log/nginx/error.log

Apache：

bash
tail -f /var/log/apache2/access.log
tail -f /var/log/apache2/error.log

Docker（本教程配套）：

bash
# Apache 日志在 wordpress 容器内
docker compose logs wordpress

38.2.4 MySQL 慢查询与错误日志 ​

bash
# MySQL 错误日志（启动失败、连接异常）
tail -f /var/log/mysql/error.log

# 慢查询日志（需先开启）
mysql> SET GLOBAL slow_query_log = 'ON';
mysql> SET GLOBAL long_query_time = 2;

# 查看慢查询
tail -f /var/log/mysql/slow.log

Docker：

bash
docker compose logs db

38.2.5 Docker 容器日志汇总 ​

本教程配套的 docker-compose.yml 环境：

bash
# 查看所有服务日志
docker compose logs

# 实时跟踪 WordPress 服务
docker compose logs -f wordpress

# 只看最近 100 行
docker compose logs --tail=100 wordpress

38.3 高频故障逐个击破 ​

38.3.1 白屏 WSOD（White Screen of Death） ​

现象：前台或后台完全空白，无任何输出。

可能原因：

  • PHP 致命错误（内存耗尽、语法错误、调用不存在的函数）；
  • 主题/插件不兼容当前 PHP 版本；
  • 数据库连接失败（但通常显示「建立数据库连接时出错」）。

排查步骤：

  1. 开启 WP_DEBUG_LOG 与 WP_DEBUG_DISPLAY（临时）：
php
// wp-config.php
define( 'WP_DEBUG', true );
define( 'WP_DEBUG_LOG', true );
define( 'WP_DEBUG_DISPLAY', true ); // 临时开启，修复后立即改回 false
  1. 刷新白屏页面，查看错误信息：
Fatal error: Allowed memory size of 134217728 bytes exhausted 
(tried to allocate 20480 bytes) in /var/www/html/wp-content/plugins/xxx/xxx.php on line 123
  1. 根据错误定位：
    • 如果是 Allowed memory size：增加 WP_MEMORY_LIMIT；
    • 如果是 Call to undefined function：插件/主题不兼容；
    • 如果是 Parse error：代码语法错误（通常是手工编辑文件时漏了分号）。

修复：

php
// 增加内存限制
define( 'WP_MEMORY_LIMIT', '256M' );
define( 'WP_MAX_MEMORY_LIMIT', '512M' ); // 后台/批量操作

如果是插件问题，通过 FTP/SSH 重命名插件目录强制停用：

bash
mv wp-content/plugins/xxx wp-content/plugins/xxx.bak

图 38-1：从开启 debug 到定位问题插件/主题的完整决策树。

38.3.2 500 / 502 / 504 错误 ​

500 Internal Server Error

现象：服务器内部错误，页面显示「500」。

可能原因：.htaccess 语法错误、PHP 内存耗尽、插件冲突。

排查：

bash
# 检查 .htaccess 是否有语法错误
apache2ctl configtest

# 查看 Apache 错误日志
tail -f /var/log/apache2/error.log

修复：如果是 .htaccess 问题，重命名后让 WordPress 重新生成：

bash
mv .htaccess .htaccess.bak
# 后台【设置 → 固定链接】点击「保存更改」重新生成

502 Bad Gateway

现象：Nginx 显示 502，表示 PHP-FPM 未响应。

可能原因：

  • PHP-FPM 进程挂掉；
  • Nginx 配置中 fastcgi_pass 的 sock 路径错误；
  • PHP-FPM 达到最大进程数（pm.max_children）。

排查：

bash
# 检查 PHP-FPM 是否运行
sudo systemctl status php8.3-fpm

# 检查 Nginx 配置中的 sock 路径
grep fastcgi_pass /etc/nginx/sites-enabled/default
# 应与 PHP-FPM 的 listen 路径一致

# 查看 PHP-FPM 日志
tail -f /var/log/php8.3-fpm.log

修复：

bash
# 重启 PHP-FPM
sudo systemctl restart php8.3-fpm

# 调整进程数（如服务器内存充足）
# /etc/php/8.3/fpm/pool.d/www.conf
pm.max_children = 20

504 Gateway Timeout

现象：请求超过 Nginx 等待时间（默认 60 秒）。

可能原因：慢插件、大数据量导出、外部 API 超时。

排查：

bash
# 查看慢查询日志
tail -f /var/log/mysql/slow.log

# 临时增加超时时间验证
# Nginx 配置：
fastcgi_read_timeout 300;

修复：定位慢插件（用 Query Monitor 插件），优化或替换。

38.3.3 「建立数据库连接时出错」 ​

现象：页面显示「建立数据库连接时出错」。

可能原因：凭据错误、DB_HOST 不可达、数据库权限不足、mysqld 未运行。

排查步骤（四步定位法）：

bash
# 第 1 步：验证凭据
mysql -u wp_user -p -h localhost wp_yoursite
# 能登录 = 凭据正确

# 第 2 步：验证 DB_HOST
ping localhost
# 或
telnet localhost 3306

# 第 3 步：验证权限
mysql> SHOW GRANTS FOR 'wp_user'@'localhost';
# 应包含 ALL PRIVILEGES ON wp_yoursite.*

# 第 4 步：验证 mysqld 状态
sudo systemctl status mysql
# 或 Docker 环境
docker compose ps db

修复：

bash
# 如果是 Docker 环境 db 容器未启动
docker compose up -d db

# 如果是权限问题
mysql> GRANT ALL PRIVILEGES ON wp_yoursite.* TO 'wp_user'@'localhost';
mysql> FLUSH PRIVILEGES;

38.3.4 重定向过多（Redirect Loop） ​

现象：浏览器提示「重定向次数过多」或 ERR_TOO_MANY_REDIRECTS。

可能原因：

  • siteurl 与 home 不一致；
  • HTTPS 强制跳转与反向代理冲突；
  • 固定链接设置错误。

排查：

bash
wp option get siteurl
wp option get home
# 两者必须一致，且与当前访问 URL 匹配

HTTPS 反向代理场景（如 Cloudflare Flexible SSL）：

php
// wp-config.php 中添加，让 WordPress 识别真实协议
if ( isset( $_SERVER['HTTP_X_FORWARDED_PROTO'] ) && $_SERVER['HTTP_X_FORWARDED_PROTO'] === 'https' ) {
    $_SERVER['HTTPS'] = 'on';
}

38.3.5 固定链接全站 404 ​

现象：首页正常，但文章页、分类页全部 404。

可能原因：.htaccess 丢失、Nginx 未配置 try_files、重写规则未刷新。

排查：

bash
# Apache：检查 .htaccess 是否存在且包含 WordPress 规则
cat .htaccess | grep "RewriteEngine"

# Nginx：检查配置中是否有 try_files
grep try_files /etc/nginx/sites-enabled/default

修复：

Apache：后台【设置 → 固定链接】点击「保存更改」重新生成 .htaccess。

Nginx：在 server 块中添加：

nginx
location / {
    try_files $uri $uri/ /index.php?$args;
}

38.3.6 登录循环（Cookies 错误） ​

现象：输入正确密码后跳回登录页，或提示「Cookies 被阻止」。

可能原因：COOKIE_DOMAIN 设置错误、siteurl 与 home 不一致、浏览器缓存。

排查：

bash
# 检查 wp-config.php 中是否有 COOKIE_DOMAIN
grep COOKIE_DOMAIN wp-config.php

# 检查 siteurl 与 home
wp option get siteurl
wp option get home

修复：

php
// 删除或修改 wp-config.php 中的 COOKIE_DOMAIN
// define( 'COOKIE_DOMAIN', 'old.com' ); // 删除这行或改为新域名

38.3.7 Allowed memory size 耗尽 ​

现象：Fatal error: Allowed memory size of xxx bytes exhausted。

可能原因：PHP 内存限制不足、某个插件/主题无限循环。

排查：

php
// wp-config.php
define( 'WP_MEMORY_LIMIT', '256M' );

如果仍报错，用 Query Monitor 插件定位是哪个查询/函数占用内存。

修复：

php
// 提高内存限制
define( 'WP_MEMORY_LIMIT', '256M' );
define( 'WP_MAX_MEMORY_LIMIT', '512M' );

// 同时调整 php.ini
memory_limit = 512M

38.3.8 上传 HTTP error ​

现象：媒体库上传图片时显示「HTTP error」。

可能原因：upload_max_filesize / post_max_size 不足、目录权限、ModSecurity 拦截。

排查：

bash
# 检查 PHP 限制
php -i | grep upload_max_filesize
php -i | grep post_max_size

# 检查 uploads 目录权限
ls -la wp-content/uploads/

修复：

ini
; php.ini
upload_max_filesize = 64M
post_max_size = 64M
max_execution_time = 300
bash
# 修复目录权限
sudo chown -R www-data:www-data wp-content/uploads/
sudo chmod -R 755 wp-content/uploads/

38.3.9 「正在执行例行维护」卡住 ​

现象：页面显示「正在执行例行维护」，超过 10 分钟仍不消失。

可能原因：更新脚本超时，.maintenance 文件残留。

排查：

bash
# 检查 .maintenance 文件是否存在及创建时间
ls -la /var/www/html/.maintenance

修复：

bash
# 手动删除
rm /var/www/html/.maintenance

# 检查是否有残留的升级临时目录
rm -rf /var/www/html/wp-content/upgrade/*

38.3.10 WP-Cron 定时任务失效 ​

现象：定时文章不发布、计划备份不执行。

可能原因：站点无访问导致 WP-Cron 不触发（WP-Cron 依赖用户访问触发）。

排查：

bash
# 查看计划任务
wp cron event list

# 手动触发到期任务
wp cron event run --due-now

修复（推荐）：改用系统 cron 每 5 分钟触发：

bash
# crontab -e
*/5 * * * * curl -s https://your-site.com/wp-cron.php?doing_wp_cron > /dev/null 2>&1

或在 wp-config.php 中禁用 WP-Cron 的页面触发，完全依赖系统 cron：

php
define( 'DISABLE_WP_CRON', true );

38.4 应急恢复完整 SOP ​

38.4.1 原理说明 ​

应急恢复的前提是有可用的备份。本章使用 第 34 章 的 ./examples/bin/backup.sh 生成的备份包，在 Docker 环境中完成恢复演练。

38.4.2 恢复操作步骤 ​

场景：站点被黑，文件被篡改，数据库被注入恶意代码，需要从备份完全恢复。

步骤 1：确认备份完整性

bash
cd wordpress-tutorial/examples

# 查看备份清单
cat backups/20261004-030000/manifest.txt

# 验证 sha256
cd backups/20261004-030000
sha256sum -c manifest.txt  # Linux
# 或
shasum -a 256 -c manifest.txt  # macOS

步骤 2：创建干净的恢复环境

bash
cd wordpress-tutorial/examples

# 停止并删除当前容器与卷（⚠️ 生产环境慎用，确认备份无误后再执行）
docker compose down -v

# 重新创建容器
docker compose up -d db wordpress

步骤 3：恢复文件

bash
BACKUP="backups/20261004-030000"

# 恢复 wp-config.php（从备份中单独提取，或重新配置）
# 恢复 wp-content
tar -xzf "$BACKUP/content.tar.gz" -C /var/www/html

步骤 4：恢复数据库

bash
# 解压并导入
gunzip -c "$BACKUP/database.sql.gz" > /tmp/restore.sql
docker compose run --rm cli wp db import /tmp/restore.sql

步骤 5：验证与修复

bash
# 检查数据库完整性
docker compose run --rm cli wp db check

# 检查 URL 是否正确（如备份来自其他环境，需 search-replace）
docker compose run --rm cli wp option get siteurl

# 刷新重写规则与缓存
docker compose run --rm cli wp rewrite flush
docker compose run --rm cli wp cache flush

步骤 6：安全检查

恢复后，参照 第 32 章 的安全响应流程：

  1. 修改所有密码（数据库、WordPress 管理员、FTP/SFTP）；
  2. 更新所有盐值（wp-config.php 中的 8 个 AUTH_KEY 等）；
  3. 检查是否有后门文件（对比官方核心文件哈希）。

本章总结 ​

本章建立了 WordPress 故障排查的完整方法论：

  1. 方法论：复现 → 分层定位 → 二分缩小 → 最小复现，先查日志再动手；
  2. 日志地图：PHP error_log、WP debug.log、Nginx/Apache、MySQL、Docker 容器日志的分层定位；
  3. 10 类高频故障：白屏、500/502/504、数据库连接错误、重定向循环、固定链接 404、登录循环、内存耗尽、上传错误、维护模式卡住、WP-Cron 失效，每个都给出了「现象 → 原因 → 排查 → 修复」的完整路径；
  4. 应急恢复：使用 ./examples/bin/backup.sh 的备份完成文件 + 数据库 + 安全检查的完整恢复；
  5. 求助自检清单：错误原文、最近变更、日志片段、环境版本四件套，让求助更高效。

至此，模块七「迁移与维护」全部完成。希望你在遇到故障时，能想起本章的一句话：「先查日志，再动手；先备份，再修复。」

动手练习 ​

练-38-01：在本地 Docker 环境故意制造一个白屏故障：修改主题 functions.php 添加一行语法错误代码，观察前台表现，然后开启 WP_DEBUG_LOG 定位并修复。

练-38-02：练习「建立数据库连接时出错」的排查：停止 db 容器，观察 WordPress 的报错页面，然后按四步排查法逐步恢复。

练-38-03：配置系统 cron 替代 WP-Cron：在本地环境修改 wp-config.php 禁用 WP-Cron，然后添加 crontab 任务每 5 分钟触发 wp-cron.php，验证定时文章是否正常发布。

练-38-04：完成一次完整的应急恢复演练：使用 ./bin/backup.sh 备份当前站点，然后 docker compose down -v 清空环境，从备份恢复，验证所有功能正常。

练-38-05：编写一份「求助帖」：假设你遇到了一个虚构的故障（如「更新插件后部分页面 404」），按照 38.5 节的自检清单格式，写出完整的求助信息，包括错误原文、环境版本、复现步骤与已尝试方案。
