第 32 章 安全防护体系 ​

🔴 进阶难度 ｜ 一句话导览：WordPress 安全不是「装个安全插件」就完事，而是一套从服务器、文件权限、wp-config、登录入口、应用代码到数据库的分层防御体系。本章先建立威胁模型（你的站会被怎么打），再给出六层加固清单的逐条操作，配套实码演示 SQL 注入、XSS、CSRF 攻防对照，最后讲入侵后的应急响应流程。

学习目标 ​

  • 理解 WordPress 站点五大常见攻击向量：暴力破解、插件漏洞、XML-RPC 滥用、文件上传、注入类攻击
  • 能解释 SQL 注入 / XSS / CSRF 的原理，并写出对应的防御代码
  • 完成六层加固清单：服务器、文件权限、wp-config、登录、应用层、数据库
  • 掌握开发侧防护规范：$wpdb->prepare、转义函数族、nonce 的完整用法
  • 掌握入侵后的标准响应流程：隔离→改密→扫马→校验核心文件→恢复→复盘
  • 能识别被挂马的典型特征，并知道搜索引擎红牌申诉流程

32.1 威胁模型：你的站会被怎么打 ​

32.1.1 原理说明 ​

建立安全体系前，先明确敌人是谁。WordPress 占全球网站四成以上，攻击者的套路高度自动化——不是「黑客盯上你」，而是扫描器 7×24 全网扫，你的站上线几分钟内就会被探测。五大高频攻击向量：

攻击向量攻击方式目标
暴力破解脚本对 /wp-login.php 高频尝试常见用户名+弱密码组合拿到后台权限
插件/主题漏洞利用已公开漏洞（CVE）攻击未更新的插件执行任意代码、写 WebShell
XML-RPC 滥用经 xmlrpc.php 一次请求试几百个密码（system.multicall）、或借 pingback 做 DDoS 放大爆破、攻击他人
文件上传利用上传校验缺陷把 .php 木马传进 uploads植入 WebShell 长期控制
注入类攻击SQL 注入读数据库、XSS 窃取管理员会话、CSRF 借管理员之手执行操作拖库、篡改、提权

对应的防御思想是纵深防御：任何一层被击穿，还有下一层兜底。入侵无法绝对避免，但可以让攻击成本高于收益、把损失控制到最小。

32.1.2 三类注入攻击原理与防御对照 ​

SQL 注入：把用户输入拼进 SQL 语句，输入里的引号闭合了原语句，攻击者的代码成了 SQL 的一部分。

php
// ❌ 错误：直接拼接用户输入。访问 ?id=1 OR 1=1 时全表数据泄露
$id = $_GET['id'];
$wpdb->get_results( "SELECT * FROM {$wpdb->posts} WHERE ID = $id" );

// ✅ 正确：$wpdb->prepare 占位符，输入永远只是「值」不会是「语句」
$wpdb->get_results(
	$wpdb->prepare( "SELECT * FROM {$wpdb->posts} WHERE ID = %d", $id )
);
// %d 整数、%s 字符串、%f 浮点；表名不能用占位符，只能用 {$wpdb->前缀} 白名单拼接

XSS（跨站脚本）：把用户输入未转义输出到页面，输入里的 <script> 被浏览器当代码执行，可窃取登录 Cookie、冒充管理员操作。

php
// ❌ 错误：评论内容直接输出，攻击者提交 <script>偷Cookie代码</script> 即生效
echo $_GET['search'];

// ✅ 正确：按输出场景选转义函数
echo esc_html( $_GET['search'] );                    // 文本节点：转义全部 HTML
echo '<a href="' . esc_url( $url ) . '">';           // URL 属性：过滤 javascript: 伪协议
echo '<input value="' . esc_attr( $title ) . '">';   // HTML 属性：转义引号防属性逃逸
echo wp_kses_post( $rich_text );                     // 富文本：只放行文章级安全标签

CSRF（跨站请求伪造）：攻击者做个恶意页面，诱使已登录的管理员访问，页面偷偷向你的站发「删除文章」请求——浏览器自动带上管理员的登录 Cookie，请求被当成管理员本人操作。防御是给每个敏感操作配一次性令牌（nonce）：

php
// 表单页：输出 nonce 隐藏域
<form method="post">
	<?php wp_nonce_field( 'wpa_delete_item_' . $item_id ); ?>
	<button type="submit">删除</button>
</form>

// 处理页：校验 nonce，验证不过直接 die
if ( ! isset( $_POST['_wpnonce'] )
	|| ! wp_verify_nonce( $_POST['_wpnonce'], 'wpa_delete_item_' . $item_id ) ) {
	wp_die( '安全校验失败' );
}
// 后台 admin-post.php 场景可用 check_admin_referer( '动作名' ) 一步校验

恶意页面伪造不出有效 nonce，伪造请求自然被拦截。

32.2 加固第①层：服务器 ​

32.2.1 操作清单 ​

  1. SSH 密钥登录，关闭密码登录：
bash
# 本地生成密钥对（已有可跳过）
ssh-keygen -t ed25519 -C "you@example.com"
# 把公钥推上服务器
ssh-copy-id user@服务器IP
# /etc/ssh/sshd_config：关闭密码与 root 直登
#   PasswordAuthentication no
#   PermitRootLogin no
sudo systemctl reload ssh
  1. 防火墙最小开放：只开 80/443/SSH 三个端口。
bash
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw allow 22/tcp    # 建议同时把 SSH 改到非标端口
sudo ufw enable
  1. fail2ban 防爆破：扫描登录失败日志，连续失败即封 IP。
bash
sudo apt install fail2ban
# /etc/fail2ban/jail.local 中启用 sshd 与 wordpress 过滤规则
# WP 侧可装 WP fail2ban 插件把登录失败写进 syslog 供 fail2ban 消费
  1. 自动安全更新：操作系统安全补丁自动打（unattended-upgrades），WordPress 小版本自动更新见 32.4 的 WP_AUTO_UPDATE_CORE：
bash
# Debian/Ubuntu：启用无人值守安全更新
sudo apt install unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades   # 交互式确认开启
  1. 数据库不暴露公网：MySQL/MariaDB 的 bind-address 保持 127.0.0.1（或内网地址），防火墙不放行 3306——远程管理走 SSH 隧道（ssh -L 3306:localhost:3306 user@服务器）。

32.3 加固第②层：文件权限 ​

32.3.1 原理与操作 ​

权限原则：进程需要的最小权限，不多给一分。写权限越大的文件越危险（被篡改=被挂马）。三个数字的含义：所有者/同组/其他人各自的「读 4 + 写 2 + 执行 1」之和——755 即 rwxr-xr-x，644 即 rw-r--r--。

bash
# 目录 755：属主可读写执行，其他人只读+进入
find /var/www/wordpress -type d -exec chmod 755 {} \;
# 文件 644：属主可读写，其他人只读
find /var/www/wordpress -type f -exec chmod 644 {} \;
# wp-config.php 600 或 640：含数据库密码与盐值，连同组用户都尽量不给读
chmod 600 /var/www/wordpress/wp-config.php

属主原则：文件属主应为部署账号，PHP 运行用户（www-data）只需读权限；只有 wp-content/uploads 等必须写入的目录才属 www-data。这样即使 PHP 代码被注入，也改不动核心文件。

禁目录浏览：没有 index 文件的目录被直接访问时，服务器默认列出文件清单（泄露结构）。Apache 在配套 apache.htaccess 中已含：

apache
<IfModule mod_autoindex.c>
	Options -Indexes   # 关掉目录列表，返回 403
</IfModule>

Nginx 默认 autoindex off，无需配置。

32.4 加固第③层：wp-config.php ​

配套 wp-config.snippet.php 中安全相关的三段：

php
// 1) 禁止后台在线编辑 PHP 文件。后台被盗后，在线编辑器是零上传
//    写木马的通道；代码修改一律走 Git/部署流程
define( 'DISALLOW_FILE_EDIT', true );

// 2) 小版本安全补丁自动更新：7.1.x 的补丁只修漏洞不改结构，风险低收益高
define( 'WP_AUTO_UPDATE_CORE', 'minor' );

// 3) 盐值：8 个随机串用于签名登录 Cookie。怀疑泄露时重新生成
//    （https://api.wordpress.org/secret-key/1.1/salt/ 在线生成整段覆盖），
//    旧 Cookie 全部失效——相当于一键踢掉所有登录会话
define( 'AUTH_KEY', '在线生成器给的随机值' );
// ...共 8 个，见配套文件

盐值轮换演练：每季度或怀疑泄露时执行一次，全站用户需重新登录，属正常预期。

32.5 加固第④层：登录安全 ​

32.5.1 基础四件套 ​

  1. 强密码：16 位以上随机串，密码管理器生成；
  2. 双因素认证（2FA）：装 WP 2FA / Two Factor 插件，登录除密码外再要手机验证码——密码泄露也进不来；
  3. 登录限次：Limit Login Attempts Reloaded 等插件，连续失败锁定 IP；
  4. 不用 admin 当用户名：自动化爆破的第一组字典就是 admin/admin。

32.5.2 登录错误模糊化（配套实码解析） ​

默认情况下，登录失败时 WordPress 会明确提示「用户名不存在」或「密码错误」——攻击者借此枚举有效用户名，再集中爆破密码。配套示例插件 ./examples/plugins/wp-academy-demo/includes/class-security.php 中的对应实现逐段解读：

php
// 构造函数：总开关控制——设置项未开启时一个过滤器都不挂，便于教学对比
if ( 1 !== (int) wpa_demo_get_option( 'harden_security' ) ) {
	return;
}

// 挂载 login_errors 过滤器：登录失败提示统一走我们的函数
add_filter( 'login_errors', [ $this, 'obfuscate_login_errors' ] );

// 无论真实错误是什么（用户名不存在/密码错），对外只有一句统一文案
public function obfuscate_login_errors() {
	return '用户名或密码不正确';
}

同类加固在该文件中还有：关闭 XML-RPC（add_filter('xmlrpc_enabled', '__return_false')）、隐藏版本号（remove_action('wp_head', 'wp_generator')）、移除暴露编辑服务的 wlwmanifest/RSD 链接、追加三个安全响应头。这些改动单看都很小，合起来砍掉了扫描器最常用的几个指纹入口。

32.5.3 「隐藏登录页」的争议 ​

把 /wp-login.php 改成 /my-secret-login/ 的插件（WPS Hide Login 等）能减少日志里的爆破噪音，但要认清它的定位：这是「隐晦式安全」（security by obscurity），不是真正的防线——它挡不住任何针对登录接口本身的攻击（REST API、XML-RPC、admin-ajax.php 的认证端点还在）。可作为减噪辅助，绝不能替代强密码 + 2FA + 限次。且要记住自定义路径，忘了会被自己锁在门外。

32.5.4 应用密码（Application Passwords）的管理 ​

WordPress 5.6+ 的应用密码给第三方服务（移动端 App、自动化脚本）颁发独立凭证，泄露后可单独吊销而不动主密码。审计入口：「用户 → 个人资料 → 应用密码」。若站点完全不用，可在用户筛选器里禁用：

php
// 全站禁用应用密码（确认无第三方服务依赖后）
add_filter( 'wp_is_application_passwords_available', '__return_false' );

32.6 加固第⑤层：应用层 ​

32.6.1 安全插件与 XML-RPC 取舍 ​

安全插件（Wordfence / Solid Security）的选型与点击级配置见 第 18 章，它们提供 WAF（Web 应用防火墙）、恶意代码扫描、登录防护的整合面板。本章聚焦其背后的取舍逻辑。

XML-RPC 的取舍：xmlrpc.php 是历史遗留的远程发布接口，如今被滥用于：① system.multicall 一次请求试上百组密码（绕过登录限次）；② pingback 被当 DDoS 放大器。默认应关闭（Nginx 直接 deny all，见 nginx-wordpress.conf；或代码层 xmlrpc_enabled 过滤器）。确认无依赖再关：Jetpack 部分功能、旧版手机 App、离线写作客户端会受影响。

32.6.2 REST API 用户枚举防护 ​

WordPress REST API 默认公开用户列表：GET /wp-json/wp/v2/users 返回所有用户名（登录名），等于把爆破字典的一半拱手送出。防护代码：

php
// 未登录访客请求用户端点时，直接返回权限错误
add_filter( 'rest_endpoints', function ( $endpoints ) {
	if ( ! is_user_logged_in() ) {
		unset( $endpoints['/wp/v2/users'] );
		unset( $endpoints['/wp/v2/users/(?P<id>[\d]+)'] );
	}
	return $endpoints;
} );

另外扫描器还常用 /?author=1 重定向枚举登录名（跳转到 /author/登录名/），可用安全插件或下面的代码拦截：

php
add_action( 'template_redirect', function () {
	if ( is_author() && ! is_user_logged_in() ) {
		wp_safe_redirect( home_url(), 301 );
		exit;
	}
} );

32.7 加固第⑥层：数据库 ​

32.7.1 三条防线 ​

  1. 随机表前缀：默认 wp_ 让自动化注入工具按固定表名猜解；安装时改成随机前缀（如 wpx7_），批量脚本直接失效。已有站修改需同步 rename 全部表并更新 wp_options/wp_usermeta 内的前缀字段，不要在运行中的站裸改。
  2. 最小权限数据库用户：配套 mysql.init.sql 演示了正确做法——WP 业务账号只授 SELECT/INSERT/UPDATE/DELETE/CREATE/DROP/ALTER/INDEX/CREATE TEMPORARY TABLES/LOCK TABLES/REFERENCES，且只授 wordpress.* 单库。绝不使用 root：即使 SQL 注入得手，也拿不到 FILE（读服务器文件）、SUPER（改全局配置）等管理权限。
  3. 备份是最后防线：所有防御都可能被零日漏洞击穿，能随时回到昨天的干净状态才是终极底气。备份策略（3-2-1 原则、自动化与恢复演练）详见 第 34 章。

32.8 补充加固：安全响应头、用户角色与日志审计 ​

32.8.1 安全响应头总览 ​

nginx-wordpress.conf 与 apache.htaccess 中已配置四个响应头，逐条理解其防御对象：

响应头防御的攻击配置要点
X-Frame-Options: SAMEORIGIN点击劫持（恶意站 iframe 嵌你的站骗点击）需要被合作方嵌入时改用 CSP frame-ancestors
X-Content-Type-Options: nosniffMIME 嗅探（上传的文本被当脚本执行）无条件开启，无副作用
Referrer-Policy: strict-origin-when-cross-originReferer 泄露完整 URL（可能含敏感参数）跨站只带 origin，平衡分析需求
Strict-Transport-SecuritySSL 剥离（降级到 HTTP 截获流量）先小 max-age 观察再加 preload，见配置文件注释

CSP（Content-Security-Policy）是更强的 XSS 防线（白名单脚本来源），但配置错误直接白屏，建议先 Content-Security-Policy-Report-Only 观察上报再转强制——这也是配套 class-security.php 不默认下发 CSP 的原因。

32.8.2 用户角色与权限最小化 ​

WordPress 五档角色（订阅者/投稿者/作者/编辑/管理员）是应用层的权限边界。规范：

  • 管理员账号 ≤ 2 个（一个日常用、一个应急备用），其余按职责给编辑/作者；
  • 日常发文不用管理员：管理员账号只用于维护操作，缩小被盗后的爆炸半径；
  • 定期审计：每季度过一遍用户列表，离职/不活跃的账号及时降级或删除；
  • 定制角色：用插件（User Role Editor）或代码 add_role()/remove_role() 裁剪权限，例如让「编辑」不能安装插件。

32.8.3 日志与审计 ​

看不见的攻击无法防御。三类日志各司其职：

  1. 服务器日志：Nginx access/error log——找爆破 IP（/wp-login.php POST 频率）、扫描器路径（/.env、/wp-config.php~）；
  2. WP 活动日志：WP Activity Log 类插件记录后台操作（谁登录、谁改了设置、谁装了插件），入侵溯源与多管理员问责的依据；
  3. 错误日志：WP_DEBUG_LOG 写到 wp-content/debug.log（生产环境见 wp-config.snippet.php 的调试三件套配置），异常的文件写入与函数报错常是入侵早期的蛛丝马迹。

威胁场景正确函数反面教材

文件上传校验完整示例：

php
add_action( 'admin_post_wpa_upload', function () {
	// 1. 权限与 nonce 双校验
	if ( ! current_user_can( 'upload_files' )
		|| ! check_admin_referer( 'wpa_upload_action', 'wpa_nonce', false ) ) {
		wp_die( '无权操作' );
	}

	$file = $_FILES['attachment'] ?? null;
	if ( ! $file || UPLOAD_ERR_OK !== $file['error'] ) {
		wp_die( '上传失败' );
	}

	// 2. 扩展名白名单（不要靠 MIME 头，浏览器可伪造）
	$allowed = [ 'jpg', 'jpeg', 'png', 'webp', 'pdf' ];
	$ext     = strtolower( pathinfo( $file['name'], PATHINFO_EXTENSION ) );
	if ( ! in_array( $ext, $allowed, true ) ) {
		wp_die( '文件类型不允许' );
	}

	// 3. 交给 WP 媒体处理：sanitize_file_name + wp_check_filetype 真实内容嗅探
	require_once ABSPATH . 'wp-admin/includes/file.php';
	$overrides = [ 'test_form' => false, 'mimes' => [ 'jpg|jpeg' => 'image/jpeg', 'png' => 'image/png', 'webp' => 'image/webp', 'pdf' => 'application/pdf' ] ];
	$result    = wp_handle_upload( $file, $overrides );

	if ( isset( $result['error'] ) ) {
		wp_die( esc_html( $result['error'] ) );
	}
	wp_safe_redirect( admin_url( 'admin.php?page=wpa&uploaded=1' ) );
	exit;
} );

纵深兜底：即使校验被绕过，nginx-wordpress.conf 中的规则也禁止执行 uploads 目录下的任何 PHP——木马落地也只是一段死代码：

nginx
location ~* ^/wp-content/uploads/.*\.php$ {
	deny all;    # 上传目录里的 PHP 只能被下载，永远不会被执行
}

32.10 入侵后应急响应 ​

32.10.1 六步流程 ​

mermaid
flowchart LR
    A[1 隔离<br/>断外网/维护模式] --> B[2 改密<br/>数据库/后台/FTP/面板全改]
    B --> C[3 扫马<br/>安全插件+人工查特征]
    C --> D[4 比对核心文件<br/>wp core verify-checksums]
    D --> E[5 恢复<br/>清马或回滚备份]
    E --> F[6 复盘<br/>找入侵入口补洞]
  1. 隔离：挂维护模式或暂时断站，阻止继续投毒、保护访客；
  2. 改密：数据库密码、WP 管理员密码、FTP/SSH、主机面板全部更换；轮换 8 个盐值踢掉所有会话；
  3. 扫马：Wordfence 全站扫描 + 人工排查 32.11.1 的挂马特征；
  4. 比对核心文件：用 WP-CLI 校验核心完整性，被篡改的文件一目了然：
bash
# 校验 WordPress 核心文件与官方版本的校验和
wp core verify-checksums
# 校验已装插件（官方库内的插件才能校验）
wp plugin verify-checksums --all
# 核心文件被改时，直接重装核心（不丢内容，内容在数据库与 wp-content）
wp core download --force --skip-content
  1. 恢复：能定位木马文件则清除；无法确认清理干净时，从入侵前的备份整机回滚更稳妥；
  2. 复盘：查日志找入侵入口（哪个 IP、利用什么漏洞、上传了什么），补洞后才算结案。不找入口的清理等于给攻击者留了原路返回的门。

32.10.2 「此站点包含恶意程序」红牌申诉 ​

Google 检测到挂马后会在搜索结果与浏览器中展示红色警告页。处理流程：

  1. 按 32.10.1 完成清理；
  2. 在 Google Search Console「安全问题」报告确认检测到的恶意 URL 已清除干净；
  3. 点击「请求审核」，说明已修复；
  4. 通常数小时~数天内解除；若审核被拒，说明仍有残留，回到第 1 步。

32.11 常见问题速查 ​

32.11.1 被挂马的典型特征 ​

  • 后台出现陌生的管理员账号（用户列表里不认识的 administrator）；
  • wp cron event list 里有可疑计划任务（名字伪装成 wp_ 开头但你不认识）；
  • 主题/插件文件里出现 eval(base64_decode(...))、gzinflate、str_rot13 等混淆代码；
  • 前台页面被注入隐藏外链（查看源码搜 display:none 的 div）；
  • 搜索引擎快照标题变成赌场/药品关键词（cloaking：只对搜索引擎展示垃圾内容）。

排查命令：

bash
# 在站点根目录搜常见木马特征（开发机上扫下载的站点副本更安全）
grep -rn --include='*.php' 'eval(base64_decode' .
grep -rn --include='*.php' 'gzinflate' .

32.11.2 安全插件与性能插件冲突 ​

Wordfence 的实时流量分析与缓存插件的页面缓存可能互掐（缓存页绕过 WAF、WAF 拦截缓存回源）。处理：① WAF 启用「在缓存之前运行」模式（Wordfence 称 Extended Protection，在 PHP 层最前端加载）；② 缓存插件的 bypass 规则与 WAF 白名单分开维护，不要指望一套规则通吃；③ 出现互掐时优先保安全插件，性能用 第 29 章 的服务器层手段补齐。

32.11.3 安全加固后「正常功能坏了」 ​

逐条回滚定位：关 XML-RPC 后 Jetpack 断连（改 Nginx 放行+限速）；DISALLOW_FILE_EDIT 后找不到主题编辑器（属预期，代码走 Git）；wp-config.php 600 后 WP 升级失败（确认属主是 PHP 用户或临时调 640）。加固的目标是「恰好够用」，不是「全锁死」。

32.11.4 收到「你的站点已被入侵」的勒索邮件 ​

声称「已黑入你的站，付比特币否则公开数据」的邮件九成是广撒网诈骗（密码来自别站泄露库）。验证方法：检查 32.11.1 的挂马特征 + wp core verify-checksums + 用户列表审计。三项都干净即可忽略邮件；若邮件里的密码确实是你正在用的，立即全站改密并启用 2FA——那说明密码在别处泄露了，而不是本站被攻破。

32.11.5 插件下架/停止维护怎么办 ​

插件从官方库下架（常见原因：作者放弃、曝出未修复漏洞）时：① 在 WordPress.org 插件页 与 WPScan 漏洞库查下架原因——是「作者弃坑」可暂缓处理，是「安全漏洞」立即停用；② 找活跃替代品迁移（导出数据优先）；③ 停用后按 第 29 章 的方法清理其残留数据（autoload 选项、自建表、定时任务）。
