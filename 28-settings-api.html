第 28 章 Settings API 与定制器进阶 ​

🔴 高级难度 ｜ 一句话导览：插件和主题都需要「配置」——插件用 Settings API 在后台做设置页，主题用定制器（Customizer）在「外观 → 自定义」里给站长实时预览。本章把两条路线都讲透：数据存哪、Settings API 五步骤、消毒回调实战、theme_mod 与 option 的存储差异、postMessage 局部刷新——全部对照配套代码的真实实现。

学习目标 ​

  • 能用决策表为一份配置选对存储位置：options / theme_mods / post_meta
  • 掌握 Settings API 五步骤：注册选项、设置区、字段、渲染页面、表单提交
  • 逐行讲透配套 class-settings.php：sanitize 回调、checkbox 缺键、add_settings_error
  • 会用 wp_parse_args 模式给数组选项做「默认值合并」读取辅助
  • 深入定制器 API：panel/section/setting/control 四层结构、sanitize_callback、postMessage + selective refresh（对照 inc/customizer.php）
  • 讲清 theme_mod 与 option 的存储差异与读取方式（get_theme_mod 前缀作用域）
  • 理解 nonce 与能力校验在两条路线中分别由谁完成、自建页面要补什么

28.1 数据存哪：决策表 ​

写配置代码之前先回答「这份数据是什么性质」：

数据性质存储读取 API典型例子
插件配置（换主题也要保留）wp_options 表get_option()每页课程数、安全加固开关
主题外观配置（跟主题走）wp_options 表（theme_mods 命名空间）get_theme_mod()主色、Hero 文案、页脚版权
单篇内容的属性wp_postmeta 表get_post_meta()课程时长、讲师（第 27 章）
用户个人偏好wp_usermeta 表get_user_meta()管理栏开关、面板折叠状态

两条经验法则：

  1. 跟功能走还是跟主题走？ 插件配置放 options（换主题不丢）；纯外观放 theme_mods（换主题自然隔离，A 主题的主色不会污染 B 主题）；
  2. 一组配置存一行：配套设置页把三个选项存成一个数组选项 wpa_demo_settings，而不是三行独立 option——减少数据库行数与读写次数，也便于整体套默认值。这是文件头注释里的明确设计决策。

28.2 Settings API 五步骤逐段精读 ​

配套 class-settings.php 是 Settings API 的完整样板：在「课程」CPT 菜单下挂一个「设置」子页面，管理数组选项 wpa_demo_settings（三个键：courses_per_page / show_instructor / harden_security）。五步拆解如下。

28.2.1 第一步：注册后台菜单（admin_menu） ​

php
public function add_submenu(): void {
	add_submenu_page(
		'edit.php?post_type=course',  // 父菜单：挂在课程 CPT 菜单下。
		'课程设置',                    // 页面标题 <title>。
		'设置',                        // 菜单显示名。
		'manage_options',             // 能力要求：只有管理员能看到。
		self::PAGE_SLUG,              // 'wpa-demo-settings'，URL 里的 page 参数。
		array( $this, 'render_page' ) // 渲染回调。
	);
}

挂在 admin_menu 钩子上（构造函数里 add_action( 'admin_menu', … )）。父菜单参数用 CPT 的 edit.php?post_type=course，让设置页与课程归属同一后台菜单——比另起顶级菜单更克制。

28.2.2 第二步：注册选项（admin_init → register_setting） ​

php
register_setting(
	self::OPTION_NAME,  // 选项组名（这里与选项名同名，教学简化）。
	self::OPTION_NAME,  // 选项名：wpa_demo_settings。
	array(
		'type'              => 'array',
		'sanitize_callback' => array( $this, 'sanitize' ),
		'default'           => self::defaults(),
	)
);

register_setting 做的事：把选项名加入「允许通过 options.php 保存的白名单」，并声明类型、默认值、消毒回调。没有注册的选项，options.php 拒绝保存——这就是 Settings API 的安全底座。

注意钩子选择：register_setting 挂 admin_init（后台请求才需要），菜单挂 admin_menu。配套构造函数两行分工明确：

php
private function __construct() {
	add_action( 'admin_menu', array( $this, 'add_submenu' ) );
	add_action( 'admin_init', array( $this, 'register_settings' ) );
}

28.2.3 第三步：设置区与字段（add_settings_section / add_settings_field） ​

php
add_settings_section(
	'wpa_demo_general',                     // 区段 id。
	'常规设置',                              // 区段标题。
	array( $this, 'render_section_description' ), // 区段说明回调。
	self::PAGE_SLUG                         // 归属页面 slug。
);

add_settings_field(
	'courses_per_page',                     // 字段 id。
	'每页课程数',                            // 字段标题（表格左列）。
	array( $this, 'field_courses_per_page' ), // 渲染回调（表格右列）。
	self::PAGE_SLUG,                        // 页面 slug。
	'wpa_demo_general',                     // 归属区段。
	array( 'label_for' => 'courses_per_page' ) // 让标题渲染成关联 input 的 label。
);

三层从属关系：页面 → 区段 → 字段。渲染时 do_settings_sections( PAGE_SLUG ) 会把该页面下所有区段和字段按注册顺序吐成表格。

28.2.4 第四步：渲染页面与字段 ​

页面回调 render_page()：

php
public function render_page(): void {
	if ( ! current_user_can( 'manage_options' ) ) {
		return; // 防御：页面级能力再查一次。
	}
	?>
	<div class="wrap">
		<h1>课程设置</h1>
		<?php settings_errors( self::OPTION_NAME ); ?>
		<form method="post" action="options.php">
			<?php
			settings_fields( self::OPTION_NAME );  // 输出 nonce + option_page 隐藏字段。
			do_settings_sections( self::PAGE_SLUG ); // 输出所有区段与字段。
			submit_button( '保存设置' );
			?>
		</form>
	</div>
	<?php
}

三个核心函数的精确职责：

  • settings_fields()：输出 nonce 字段、option_page（告诉 options.php 这是哪个选项组）、action/_wp_http_referer 等隐藏字段——少它整个表单直接报废；
  • do_settings_sections()：按注册结构渲染区段和字段；
  • settings_errors()：显示消毒回调里 add_settings_error() 累积的错误/成功消息。

字段回调的 HTML 纪律（以数字字段为例）：

php
public function field_courses_per_page(): void {
	$value = (int) self::get_option( 'courses_per_page' );
	printf(
		'<input type="number" min="1" max="50" step="1" id="courses_per_page" name="%1$s[courses_per_page]" value="%2$d" class="small-text"> <span class="description">篇课程（允许范围 1-50）</span>',
		esc_attr( self::OPTION_NAME ),
		$value
	);
}

字段 name 必须是「选项名[键名]」形式（wpa_demo_settings[courses_per_page]）——文件头注释的坑点原话：「否则数据不会进入 register_setting 注册的数组选项」。这是数组选项存一行（28.1 法则二）在表单层的对应写法。

28.2.5 第五步：消毒回调（sanitize）——安全的核心 ​

options.php 收到 POST 后的处理顺序：nonce 校验 → 能力校验（manage_options）→ 白名单检查 → 调用你的 sanitize_callback → 写库。文件头注释把这条链写得很清楚，所以 sanitize 里不需要自己验 nonce。

配套 sanitize() 全文值得逐行读：

php
public function sanitize( $input ) {
	$input    = is_array( $input ) ? $input : array();
	$defaults = self::defaults();
	$clean    = array();

	// 每页课程数：正整数 + 范围 1-50，越界回退默认并展示错误。
	$per_page = isset( $input['courses_per_page'] ) ? absint( $input['courses_per_page'] ) : $defaults['courses_per_page'];

	// Yoda 写法：字面量放在比较运算符左侧。
	if ( 1 > $per_page || 50 < $per_page ) {
		add_settings_error(
			self::OPTION_NAME,
			'wpa-demo-per-page-range',
			'「每页课程数」必须是 1 到 50 之间的整数，已恢复为默认值 6。',
			'error'
		);
		$per_page = $defaults['courses_per_page'];
	}
	$clean['courses_per_page'] = $per_page;

	// 复选框未勾选时键不存在，按 0 处理。
	$clean['show_instructor'] = empty( $input['show_instructor'] ) ? 0 : 1;
	$clean['harden_security'] = empty( $input['harden_security'] ) ? 0 : 1;

	return $clean;
}

四个教学点逐个说：

  1. 不信任输入形状：第一行 is_array 守卫——$input 可能根本不是数组（构造的畸形请求）；
  2. 服务端必须重新校验范围：HTML 的 min="1" max="50" 只是用户体验，改包提交 9999 照样到达服务端。absint 转非负整数 → 范围钳制 → 越界时 add_settings_error 给用户可见的反馈，同时回退默认值；
  3. checkbox 的缺键陷阱（文件头注释重点）：复选框未勾选时浏览器根本不提交这个键——$input['show_instructor'] 不存在。直接取会 PHP Warning 且语义错误，必须用 empty() 判定为 0。这是 Settings API 最高频的坑，没有之一；
  4. 返回全新数组：$clean 只包含显式清洗过的键，输入里的任何多余键（恶意注入的）全部被丢弃——白名单式重建。

28.2.6 读取辅助：wp_parse_args 模式 ​

配套的读取辅助是「数组选项 + 默认值合并」的标准模式：

php
public static function get_option( string $key = '' ) {
	$stored  = get_option( self::OPTION_NAME, array() );
	$options = wp_parse_args( is_array( $stored ) ? $stored : array(), self::defaults() );

	if ( '' === $key ) {
		return $options;
	}

	return $options[ $key ] ?? null;
}

为什么需要 wp_parse_args：数据库里的数组可能是旧版本存的（缺新加的键），或被手动改过（不是数组）。合并 defaults() 后，任何键都有定义好的值——业务代码里永远不需要 isset 防御。文件头注释称之为「单一事实来源」：注册、清洗、读取三处共用同一个 defaults()。

配套还提供了一个全局函数包装，主题/其它插件直接调用：

php
function wpa_demo_get_option( string $key = '' ) {
	return WPA_Settings::get_option( $key );
}

前台用法示例：wpa_demo_get_option( 'courses_per_page' ) 拿到每页课程数；harden_security 键被配套的 WPA_Security 类读取，决定安全加固是否启用——设置页与功能模块通过这一个键解耦。

28.2.7 设置的消费端：一次真实的读取 ​

「设置页只是写入端，真正的价值在消费端」。配套 class-security.php 展示了消费的标准姿势——构造函数第一行就读开关：

php
// class-security.php 节选：未开启加固时直接不挂任何钩子。
if ( 1 !== (int) wpa_demo_get_option( 'harden_security' ) ) {
	return;
}

三个细节值得学：① (int) 强转 + Yoda 比较——选项存的是 0/1，防御数据库里可能出现的字符串形态；② 读取发生在构造函数（plugins_loaded 链路），早于所有被控制的钩子，保证「关掉开关 = 功能完全不激活」而不是「激活了再拆」；③ 开关关闭时整个类零钩子、零输出——用户感知不到它的存在。这就是「设置驱动功能」的干净闭环：UI 写入（Settings API）→ 存储（options 数组）→ 消费（读取辅助函数）→ 行为（钩子挂载与否）。

28.3 定制器 API 深入 ​

28.3.1 原理说明：四层结构 ​

定制器（外观 → 自定义）的对象模型四层：Panel（面板）→ Section（区段）→ Setting（设置）→ Control（控件）。Setting 管数据（存哪、默认值、消毒），Control 管界面（输入框类型），Section 分组，Panel 再组 Section。

对照配套 inc/customizer.php 的结构：一个面板 wpa_theme_options（WP Academy 主题选项），三个区段 wpa_colors（主色）/ wpa_hero（首页 Hero）/ wpa_footer（页脚版权），全部挂在 customize_register 钩子上。

28.3.2 setting + control 的最小对 ​

以主色为例：

php
$wp_customize->add_setting(
	'wpa_accent_color',
	array(
		'default'           => '#2563eb',
		'type'              => 'theme_mod',          // 存储方式：theme_mod（默认）。
		'sanitize_callback' => 'sanitize_hex_color', // 核心自带的颜色消毒。
		'capability'        => 'edit_theme_options', // 能力要求。
	)
);

$wp_customize->add_control(
	new WP_Customize_Color_Control(  // 颜色选择器控件（核心自带）。
		$wp_customize,
		'wpa_accent_color',          // 与 setting 同名 → 自动绑定。
		array(
			'label'   => __( '主题主色（链接 / 按钮 / Hero）', 'wp-academy' ),
			'section' => 'wpa_colors',
		)
	)
);

要点：

  • 同名即绑定：control 的第一个参数（id）与 setting id 相同，二者自动关联，不用显式指定 settings；
  • 每个 setting 都显式声明 sanitize_callback——文件头注释列此为教学重点。定制器输入同样要消毒：sanitize_text_field（纯文本）/ esc_url_raw（URL）/ wp_kses_post（富文本）/ 自定义 wpa_sanitize_checkbox（复选框）；
  • checkbox 消毒的坑（文件头注释原话）：定制器保存后 checkbox 取到 '' 或 1，配套的 wpa_sanitize_checkbox() 统一转成 bool：
php
function wpa_sanitize_checkbox( $checked ) {
	return ( isset( $checked ) && true === (bool) $checked );
}

28.3.3 theme_mod vs option：存储差异 ​

setting 的 type 决定存储位置：

type存储读取作用域
theme_mod（默认）options 表 theme_mods_{主题名} 一行数组get_theme_mod( $key, $default )跟随主题：换主题互相隔离
optionoptions 表独立一行get_option( $key )全局：换主题依然存在

配套主题全部用 theme_mod——外观配置跟主题走，这正是 28.1 决策表的实践。

get_theme_mod() 的「前缀作用域」值得一句说明：它实际读写的是 theme_mods_wp-academy 这个 option 行（行名含主题目录名），所以不同主题的同名 theme_mod 互不干扰。

默认值不入库（文件头注释的设计决策）：所有默认值在读取处给出——

php
$wpa_hero_title = get_theme_mod( 'wpa_hero_title', __( '从零开始，系统学习 WordPress', 'wp-academy' ) );

用户从未保存时数据库里没有任何行，get_theme_mod 返回第二参数。好处：默认值将来调整时，老站自动跟进新默认，而不是被建库时的旧值锁死。配套 front-page.php 的整段 Hero 读取都是这个模式。

28.3.4 postMessage 与 selective refresh ​

定制器默认的预览方式是 refresh——每次改动整页 iframe 刷新，慢且闪烁。postMessage 让改动通过 JS 消息直达预览页，毫秒级无刷新。配套演示了两种 postMessage 的落地方式：

方式一：纯 JS 改写（站点标题）——

php
$blogname_setting = $wp_customize->get_setting( 'blogname' );
if ( $blogname_setting ) {
	$blogname_setting->transport = 'postMessage';
}

transport 改为 postMessage 后，需要一段 JS 监听消息并就地改写 DOM。虽然配套主题刻意不引入额外 JS（文件头注释：「避免为教学主题引入额外的 customize-preview.js」），但这个文件的标准写法必须会：

javascript
// assets/js/customize-preview.js（示例，非配套文件）
// 入队方式：挂 customize_preview_init 钩子，只在定制器预览页加载。
( function ( $ ) {
	// 站点标题：改输入框的瞬间就地替换文本。
	wp.customize( 'blogname', function ( setting ) {
		setting.bind( function ( newValue ) {
			$( '.site-title a' ).text( newValue );
		} );
	} );

	// 主色：直接改写 CSS 变量，与 wpa_customizer_inline_css 的 :root 方案联动。
	wp.customize( 'wpa_accent_color', function ( setting ) {
		setting.bind( function ( newValue ) {
			document.documentElement.style.setProperty( '--wpa-accent', newValue );
		} );
	} );
} )( jQuery );

对应的 PHP 入队（挂 customize_preview_init，不是 wp_enqueue_scripts）：

php
/**
 * 定制器预览页专用 JS。
 *
 * 坑点：必须挂 customize_preview_init；挂 wp_enqueue_scripts 会污染前台。
 *
 * @return void
 */
function wpa_customize_preview_js() {
	wp_enqueue_script(
		'wpa-customize-preview',
		WPA_URI . '/assets/js/customize-preview.js',
		array( 'customize-preview' ), // 依赖核心的预览通信库。
		WPA_VERSION,
		true
	);
}
add_action( 'customize_preview_init', 'wpa_customize_preview_js' );

wp.customize( settingId ).bind() 是定制器 JS API 的核心模式：setting 一变，回调立即收到新值。选择纯 JS（方式一）还是 selective refresh（方式二）的经验法则：纯文本/颜色/可见性用纯 JS（零请求、零延迟）；结构复杂或含 PHP 渲染逻辑的用 selective refresh（保真但有一次 AJAX）。

方式二：selective refresh 局部刷新（页脚版权）——setting 声明 postMessage + 注册一个 partial：

php
$wp_customize->add_setting(
	'wpa_footer_text',
	array(
		'default'           => '',
		'type'              => 'theme_mod',
		'transport'         => 'postMessage',      // 关键：消息驱动而非整页刷新。
		'sanitize_callback' => 'wp_kses_post',
		'capability'        => 'edit_theme_options',
	)
);

if ( isset( $wp_customize->selective_refresh ) ) {
	$wp_customize->selective_refresh->add_partial(
		'wpa_footer_text',
		array(
			'selector'        => '.site-footer-text',   // 页脚里对应的 DOM 节点。
			'settings'        => array( 'wpa_footer_text' ),
			'render_callback' => function () {
				$footer_text = get_theme_mod( 'wpa_footer_text', '' );
				if ( '' !== $footer_text ) {
					return wp_kses_post( $footer_text );
				}
				return '&copy; ' . esc_html( date_i18n( 'Y' ) ) . ' ' . esc_html( get_bloginfo( 'name', 'display' ) );
			},
		)
	);
}

工作原理：setting 改动 → JS 消息通知预览页 → 核心找到绑定该 setting 的 partial → 用 AJAX 调 render_callback 重新渲染 selector 匹配的局部 DOM → 就地替换。不需要你写一行 JS，又避免了整页刷新。文件头注释的坑点提醒：selective_refresh 组件只在定制器界面才实例化，用前必须 isset 判断。

🔗 render_callback 的输出与 footer.php 里 .site-footer-text 的真实输出逐字一致（含「留空自动生成 © 年份 站点名」的兜底逻辑）——partial 若与模板输出不一致，预览与前台就会出现「所见非所得」。

28.3.5 定制器值如何生效：内联 CSS 变量 ​

主色改完怎么影响前台？配套的做法是 wp_head 输出 CSS 变量覆盖：

php
function wpa_customizer_inline_css() {
	$accent = get_theme_mod( 'wpa_accent_color', '#2563eb' );

	if ( '' === $accent ) {
		return;
	}

	printf(
		'<style id="wpa-customizer-inline-css">:root{--wpa-accent:%s;}</style>' . "\n",
		esc_attr( $accent )
	);
}
add_action( 'wp_head', 'wpa_customizer_inline_css', 100 );

main.css 里所有主色引用都写 var(--wpa-accent)，style.css 里有同值兜底（:root { --wpa-accent: #2563eb; }），定制器的内联 style 用优先级 100 晚于入队样式打印，自然覆盖默认值。注意 esc_attr 二次保险（文件头注释）：颜色值输出到 style 场景仍要转义。改主色 = 改一个变量，全站级联生效——这是「CSS 变量 + 定制器」的现代标准组合。

28.4 nonce 与能力校验：两条路线的责任边界 ​

Settings API（options.php）定制器
noncesettings_fields() 输出，options.php 自动 check_admin_referer()定制器框架自带
能力options.php 统一查 manage_options；页面渲染时再查一次做防御每个 setting 的 capability（默认 edit_theme_options）
你要补什么什么都不用（走 options.php 的前提下）声明好 sanitize_callback 与 capability

文件头注释的警告值得重复：若改为自建处理端点（admin-post.php / admin-ajax.php / REST），则必须自行 check_admin_referer() 或 wp_verify_nonce() + current_user_can()，缺一不可。配套小工具章（第 26 章）同理：小工具保存走核心流程，自己只做数据清洗。

一句话原则：走核心管道，安全由核心兜底；自建管道，安全全部由你负责。

28.5 两条路线如何选型 ​

同一个配置需求摆面前，放设置页还是定制器？决策依据是「配置的性质」和「使用者的预期」：

维度Settings API 设置页定制器
数据性质功能性配置（行为开关、数值参数）外观性配置（颜色、文案、布局开关）
实时预览价值低（功能开关预览无意义）高（颜色/文案必须所见即所得）
存储惯例options（跟功能走，换主题保留）theme_mods（跟主题走，换主题隔离）
用户心智「插件/系统的设置」「这个主题长什么样」
承载者插件（或主题的 functions.php）几乎总是主题

对照配套代码的两个真实案例，边界划得非常干净：

  • harden_security（安全加固开关）放插件设置页——它是功能配置，换主题后安全策略不应失效，存 wpa_demo_settings 数组选项；
  • wpa_accent_color（主色）放定制器——它是外观配置，站长改的时候必须立刻看到效果，存 theme_mods_wp-academy。

判不清时的经验问题：「换主题之后，这个配置还应该生效吗？」 应该 → 设置页 + options；不应该 → 定制器 + theme_mods。

一个反例提醒：有些主题把「备案号」「统计代码」塞进定制器。这在功能上能跑，但换主题即丢，且统计代码属于功能性配置——更稳的做法是放主题设置页（Settings API）或交给插件。定制器的地盘始终应该是「外观」。

💡 还有一个隐藏第四路线：register_setting() 注册的选项配合 'show_in_rest' => true 可以暴露给古腾堡侧栏/区块编辑器做「编辑器内设置」，这是区块时代的进阶玩法；本模块先吃透两条经典路线，REST 暴露在第 27 章的 register_post_meta 已有同构示范。

28.6 常见问题（本章汇总） ​

  1. 保存后一片空白/选项没存上：settings_fields() 的参数（选项组名）与 register_setting 第一参数不一致；或字段 name 没写成「选项名[键名]」。这是 Settings API 两大经典事故；
  2. checkbox 总是存不上/关不掉：sanitize 里直接读了 $_POST 或没处理缺键。必须用 empty( $input['x'] ) ? 0 : 1 模式（见 28.2.5）；
  3. postMessage 不刷新：setting 的 transport 没改成 postMessage；或 partial 的 selector 与模板实际 DOM 不匹配；或 render_callback 输出与模板不一致；
  4. sanitize_callback 报「回调不存在」：字符串形式的回调（如 'sanitize_hex_color'）在 admin_init 时可用；类方法回调必须是 array( $this, 'sanitize' ) 且方法 public；
  5. get_theme_mod 拿到旧值：定制器里改的是预览态，未点「发布」不会写库——这是特性不是 bug；代码里调试时用 wp cache flush 排除对象缓存干扰。
