第 35 章 数据迁移全流程 ​

🟡 进阶难度 ｜ 一句话导览：迁移不是简单的「复制粘贴」——文件要完整、数据库要一致、URL 要替换、缓存要刷新。本章把迁移拆成可执行的流水线，覆盖本地到服务器、服务器到服务器、只换域名三大场景，并逐段精读配套脚本 ./examples/bin/migrate.sh。

学习目标 ​

  • 能画出 WordPress 迁移的完整流程图，理解每一步的必要性
  • 掌握本地 Docker 站点迁移到云服务器的完整操作序列
  • 掌握服务器到服务器的零停机迁移技巧
  • 能使用 Duplicator / All-in-One WP Migration 完成打包迁移
  • 逐段精读并定制 ./examples/bin/migrate.sh，理解 dry-run 预演与序列化感知替换
  • 掌握迁移后的 8 项验证清单，确保无遗漏

35.1 迁移总流程 ​

35.1.1 原理说明 ​

WordPress 迁移的本质是在目标环境重建一个与源站完全一致的状态。这个状态由文件系统、数据库、运行时配置三部分构成。迁移失败通常不是因为「少拷了文件」，而是因为：

  • URL 不一致：数据库里存的是旧域名，新环境访问时跳回旧站；
  • 序列化数据损坏：直接文本替换导致 s:24:"http://old.com" 长度不匹配，小工具与主题设置丢失；
  • 路径差异：源站放在 /home/user/ 而目标站是 /var/www/html/，绝对路径引用失效；
  • 缓存污染：旧域名被缓存到页面缓存、对象缓存或 CDN 中。

因此，任何可靠的迁移方案都必须包含：备份 → 传输 → 导入 → 替换 → 验证 → 观察期 六个环节，缺一不可。

mermaid
flowchart TD
    A[迁移前备份<br/>备份文件+数据库] --> B[传输文件<br/>themes/plugins/uploads/wp-config.php]
    B --> C[导入数据库<br/>MySQL 导入 SQL]
    C --> D[URL 替换<br/>search-replace 旧域名→新域名]
    D --> E[修改配置<br/>wp-config.php / DNS]
    E --> F[验证<br/>首页/文章/图片/后台/表单]
    F --> G{验证通过？}
    G -->|否| H[排查修复<br/>参考第 38 章]
    H --> D
    G -->|是| I[DNS 切换或旧站下线]
    I --> J[旧站观察期<br/>7–14 天保留]
    J --> K[迁移完成]

💡 先备份，再迁移。本章所有操作都建立在已有有效备份的前提下。如果你还没有备份，请先回到 第 34 章 完成备份。

35.1.2 迁移前检查清单 ​

检查项合格标准不满足时的处理
源站备份数据库与文件备份已验证可恢复先完成 第 34 章 恢复演练

35.2 场景一：本地 → 服务器 ​

35.2.1 原理说明 ​

本地开发环境（如 Docker Compose）与生产服务器的核心差异在于：

  1. 数据库连接：本地容器用 db:3306 服务名，服务器用 localhost 或云数据库地址；
  2. 文件路径：本地是 /var/www/html（容器内）或项目目录（宿主机），服务器可能是 /var/www/vhosts/...；
  3. URL：本地是 http://localhost:8080，服务器是 https://www.example.com。

因此迁移的核心工作就是适配差异：导出数据库 → 上传文件 → 修改 wp-config.php → 替换 URL → 验证。

35.2.2 点击级操作（以 Docker 本地站为源） ​

以下操作基于教程配套的 ./examples/docker-compose.yml 本地环境。

步骤 1：导出数据库

bash
# 进入本地环境目录
cd wordpress-tutorial/examples

# 使用 WP-CLI 导出数据库到宿主机
docker compose run --rm cli wp db export /tmp/local-export.sql

# 或者直接在宿主机执行（如果已映射端口）
docker compose exec db mysqldump -u root -p wordpress > local-export.sql

步骤 2：打包上传文件

bash
# 打包 wp-content 下需要迁移的三个目录
tar -czf local-content.tar.gz \
  -C /var/www/html \
  wp-content/themes \
  wp-content/plugins \
  wp-content/uploads

如果 themes/plugins 是 bind mount 挂载的（如 ./themes/wp-academy），直接在宿主机打包即可：

bash
tar -czf local-content.tar.gz \
  -C wordpress-tutorial/examples \
  themes/wp-academy \
  plugins/wp-academy-demo

步骤 3：上传文件到服务器

使用 scp 或 rsync 上传：

bash
# 上传文件包
scp local-content.tar.gz user@your-server:/tmp/

# 上传数据库导出文件
scp local-export.sql user@your-server:/tmp/

步骤 4：服务器上解压并准备 WordPress

在服务器上执行：

bash
# 创建网站目录（根据你的面板或规范调整）
sudo mkdir -p /var/www/html/your-site
sudo chown -R www-data:www-data /var/www/html/your-site

# 解压文件到 wp-content 上级目录
tar -xzf /tmp/local-content.tar.gz -C /var/www/html/your-site/

步骤 5：服务器上创建数据库并导入

bash
# 登录 MySQL 创建数据库与用户
mysql -u root -p <<'SQL'
CREATE DATABASE wp_yoursite CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'wp_user'@'localhost' IDENTIFIED BY '强密码';
GRANT ALL PRIVILEGES ON wp_yoursite.* TO 'wp_user'@'localhost';
FLUSH PRIVILEGES;
SQL

# 导入数据
mysql -u wp_user -p wp_yoursite < /tmp/local-export.sql

步骤 6：配置 wp-config.php

将服务器上的 wp-config.php 改为：

php
// 数据库连接信息（服务器环境）
define( 'DB_NAME', 'wp_yoursite' );
define( 'DB_USER', 'wp_user' );
define( 'DB_PASSWORD', '强密码' );
define( 'DB_HOST', 'localhost' ); // 或云数据库地址
define( 'DB_CHARSET', 'utf8mb4' );
define( 'DB_COLLATE', '' );

// 表前缀（必须与本地导出时一致）
$table_prefix = 'wp_';

// 站点 URL（必须改为服务器域名）
define( 'WP_HOME', 'https://www.example.com' );
define( 'WP_SITEURL', 'https://www.example.com' );

// 其他配置...

💡 本地 Docker 环境的 wp-config.php 通常由镜像入口脚本自动生成，迁移时不要直接复制本地的 wp-config.php，而是在服务器上基于 wp-config-sample.php 重新生成，只保留表前缀和自定义常量。

步骤 7：执行 URL 替换

这是最关键的一步。使用 WP-CLI 的 search-replace 替换数据库中的旧 URL：

bash
# 进入服务器上的 WordPress 目录
cd /var/www/html/your-site

# 先 dry-run 预演，查看影响范围
wp search-replace 'http://localhost:8080' 'https://www.example.com' --all-tables --skip-columns=guid --dry-run

# 确认无误后正式执行
wp search-replace 'http://localhost:8080' 'https://www.example.com' --all-tables --skip-columns=guid

# 刷新重写规则与缓存
wp rewrite flush
wp cache flush

步骤 8：验证

打开 https://www.example.com 检查：

  1. 首页是否正常显示；
  2. 点击几篇文章，确认内容完整且图片能加载；
  3. 进入 https://www.example.com/wp-admin 能否登录；
  4. 后台【设置 → 固定链接】点击「保存更改」刷新重写规则；
  5. 检查浏览器开发者工具是否有 Mixed Content 警告。

图 35-1：从本地 Docker 导出到服务器验证通过的完整时序，标注了各环节的预估耗时。

35.2.3 常见问题 ​

Q：迁移后图片 404？ 检查数据库中 wp_posts 表的 guid 列与 wp_postmeta 的 _wp_attached_file 元数据。如果 guid 被替换成了新域名但文件路径没变，或反之，都会导致图片加载失败。更常见的原因是 search-replace 没有替换完整——有些图片 URL 以 http://localhost:8080 存，有些以 //localhost:8080（协议相对）存。需要再执行一次替换：

bash
wp search-replace '//localhost:8080' '//www.example.com' --all-tables --skip-columns=guid

Q：后台登录死循环？ 通常是 siteurl 与 home 的协议不一致（一个 http 一个 https），或 wp-config.php 中定义了 WP_HOME / WP_SITEURL 与数据库中的值冲突。检查：

bash
wp option get siteurl
wp option get home

两者必须一致，且与 wp-config.php 中的定义（如果存在）一致。

35.3 场景二：服务器 → 服务器 ​

35.3.1 原理说明 ​

服务器到服务器的迁移比本地到服务器更复杂，因为涉及零停机切换和 DNS 传播延迟。核心策略是：

  1. DNS TTL 提前调低：在迁移前 24–48 小时，将旧域名的 A 记录 TTL 从默认的 3600 秒（1 小时）或更长，调低到 300 秒（5 分钟）。这样切换后 DNS 传播更快；
  2. 双机并行：在新服务器完成迁移并验证通过后，再切换 DNS；
  3. 旧站观察期：DNS 切换后保留旧站 7–14 天，防止部分用户仍解析到旧 IP。

35.3.2 零停机迁移操作 ​

步骤 1：准备新服务器

在新服务器上完成环境搭建（PHP 8.3 + MySQL 8 / MariaDB 10.11 + Web 服务器），确保版本与旧服务器兼容。

步骤 2：使用 rsync 同步文件（增量）

bash
# 首次全量同步（在旧服务器上执行，或从第三方跳板机）
rsync -avz --delete \
  /var/www/html/wp-content/ \
  user@new-server:/var/www/html/your-site/wp-content/

# 迁移前 1 小时执行最后一次增量同步，确保文件一致
rsync -avz --delete \
  /var/www/html/wp-content/ \
  user@new-server:/var/www/html/your-site/wp-content/

步骤 3：旧站开启维护模式

在旧服务器上创建 .maintenance 文件，阻止新写入：

bash
# 在旧服务器 WordPress 根目录创建维护文件
echo '<?php $upgrading = time(); ?>' > /var/www/html/.maintenance

或使用维护模式插件（如 WP Maintenance Mode）显示友好的维护页面。

步骤 4：导出并导入数据库

bash
# 旧服务器导出
mysqldump -u wp_user -p wp_yoursite --single-transaction > /tmp/final-export.sql

# 传输到新服务器
scp /tmp/final-export.sql user@new-server:/tmp/

# 新服务器导入
mysql -u wp_user -p wp_yoursite < /tmp/final-export.sql

步骤 5：URL 替换与配置调整

在新服务器上执行（如果域名不变，跳过 URL 替换；如果域名也变，执行替换）：

bash
# 仅当域名变化时执行
wp search-replace 'https://old.com' 'https://new.com' --all-tables --skip-columns=guid

步骤 6：验证新站

修改本地 hosts 文件，将新域名指向新服务器 IP，进行完整验证（见 35.5 节）。

步骤 7：切换 DNS

验证通过后，在 DNS 控制台将 A 记录指向新服务器 IP。由于之前已将 TTL 调低到 300 秒，5 分钟内大部分用户会解析到新服务器。

步骤 8：旧站观察期

DNS 切换后，保留旧服务器 7–14 天：

  • 监控旧服务器访问日志，确认无新请求后再下线；
  • 如果发现问题，可立即将 DNS 切回旧服务器；
  • 旧站下线前，再次确认新站数据完整。

图 35-2：从 TTL 调低到旧站下线的完整时间线，标注了各环节的先后顺序。

35.3.3 常见问题 ​

Q：DNS 已切换，但部分用户仍访问旧站？ 这是正常的 DNS 传播延迟。TTL 300 秒意味着最长 5 分钟，但某些运营商或本地 DNS 缓存可能不遵守 TTL。旧站保留期就是为了应对这种情况。

Q：迁移后订单/评论丢失？ 零停机迁移的「最后一公里」问题：DNS 切换期间，可能有用户在旧站提交了新订单或评论。解决方式：

  • 在切换前 1 小时开启维护模式，阻止新写入；
  • 或使用「双写」策略（高级，需自定义代码）；
  • 或接受少量数据丢失，切换后手动补录。

35.4 场景三：只换域名 ​

35.4.1 原理说明 ​

只换域名不换服务器是最简单的迁移场景。文件和数据库都不动，只需要：

  1. 新域名解析到同一服务器；
  2. Web 服务器配置新域名的虚拟主机；
  3. 数据库中替换旧 URL 为新 URL；
  4. 刷新缓存与重写规则。

35.4.2 操作步骤 ​

步骤 1：DNS 与虚拟主机

在 DNS 控制台将新域名 A 记录指向服务器 IP，并在 Web 服务器（Nginx/Apache）中添加新域名的虚拟主机配置，指向同一 WordPress 目录。

步骤 2：数据库 URL 替换

bash
cd /var/www/html/your-site

# 替换主域名
wp search-replace 'https://old.com' 'https://new.com' --all-tables --skip-columns=guid

# 如果旧站有 www 和非 www 混用，还需替换另一种形式
wp search-replace 'https://www.old.com' 'https://www.new.com' --all-tables --skip-columns=guid

步骤 3：配置 wp-config.php（可选）

php
define( 'WP_HOME', 'https://www.new.com' );
define( 'WP_SITEURL', 'https://www.new.com' );

步骤 4：刷新与验证

bash
wp rewrite flush
wp cache flush

验证新域名访问正常后，在旧域名的虚拟主机中配置 301 重定向到新域名。

35.5 插件方案：Duplicator 与 All-in-One WP Migration ​

35.5.1 原理说明 ​

迁移插件将「导出数据库 + 打包文件 + 生成安装器」整合为一步操作，适合不熟悉命令行的用户。其原理是：

  • Duplicator：生成一个独立的 PHP 安装器（installer.php）和压缩包（archive.zip），在新服务器上访问 installer.php 即可完成数据库导入与 URL 替换；
  • All-in-One WP Migration：生成 .wpress 格式的专用包，通过插件界面导入，自动处理 URL 替换与序列化数据。

35.5.2 Duplicator 点击级操作 ​

步骤 1：创建包

进入【Duplicator → 创建新包】：

  1. 设置：输入包名称（如 site-migration-20261004）；
  2. 扫描：插件会扫描站点大小与文件数量，提示可能的问题（如大文件、权限不足）；
  3. 构建：点击「创建」，等待打包完成。

图 35-3：Duplicator 的打包向导界面，显示扫描结果与构建按钮。

步骤 2：下载安装器与压缩包

构建完成后，下载两个文件：

  • installer.php：安装器脚本；
  • 20261004_site-migration_xxx.zip：压缩包。

步骤 3：在新服务器运行安装器

  1. 通过 FTP/SFTP 将两个文件上传到新服务器的网站根目录；
  2. 确保目录为空（或仅有这两个文件）；
  3. 浏览器访问 https://new-server-ip/installer.php；
  4. 按向导填写新数据库信息、新 URL；
  5. 完成安装后，按提示删除安装器文件。

35.5.3 All-in-One WP Migration 点击级操作 ​

步骤 1：导出

进入【All-in-One WP Migration → 导出】：

  1. 点击「导出到」→「文件」；
  2. 等待导出完成，下载 .wpress 文件。

步骤 2：导入

在新站点安装同名插件，进入【导入】：

  1. 拖放或选择 .wpress 文件；
  2. 插件会自动解压、导入数据库、替换 URL。

⚠️ 免费版有 512MB 大小限制。如果站点超过此限制，需要购买付费扩展或使用其他方案。

35.5.4 常见问题 ​

Q：Duplicator 安装器提示「无法连接数据库」？ 检查新服务器上的数据库用户是否已创建，且密码正确。Duplicator 不会自动创建数据库，只负责导入。

Q：All-in-One WP Migration 导入卡住？ 通常是文件上传大小限制或执行时间限制。修改 php.ini：

ini
upload_max_filesize = 512M
post_max_size = 512M
max_execution_time = 300

35.6 逐段精读 migrate.sh ​

35.6.1 原理说明 ​

./examples/bin/migrate.sh 是教程配套的 URL 迁移脚本，封装了 WP-CLI search-replace 的最佳实践：自动备份、dry-run 预演、人工确认、跳过 guid 列、刷新缓存。下面逐段精读。

35.6.2 脚本逐段精读 ​

第一段：参数检查 ​

bash
if [ "$#" -ne 2 ]; then
    cat >&2 <<'USAGE'
用法错误：必须提供旧 URL 与新 URL 两个参数。
...
USAGE
    exit 2
fi
  • $# 检查参数个数，必须为 2；
  • >&2 将用法输出到标准错误，符合 Unix 惯例；
  • 退出码 2 是约定俗成的「用法错误」码。
bash
OLD_URL="${1%/}"
NEW_URL="${2%/}"

${var%/} 去掉末尾的斜杠，确保替换串一致。例如 http://example.com/ 和 http://example.com 会被视为不同 URL，但用户通常意图相同。

第二段：目录定位与 WP-CLI 封装 ​

bash
wp_cli() {
    docker compose run --rm -T cli wp "$@"
}

定义函数封装 docker compose run --rm -T cli wp，后续所有 WP-CLI 命令都通过 wp_cli 调用，保证一致性。

第三段：迁移前自动备份 ​

bash
wp_cli db export - | gzip -c -9 > "$PRE_BACKUP"

迁移只改数据库不动文件，因此只备份数据库。db export - 输出到标准输出，管道给 gzip 压缩。

第四段：dry-run 预演 ​

bash
wp_cli search-replace "$OLD_URL" "$NEW_URL" --all-tables --dry-run
  • --all-tables：不仅替换 wp_ 前缀的表，还扫描同一数据库中所有表（兼容多站点、历史残留表）；
  • --dry-run：只统计将影响的行数，不实际修改数据库。

这是防止误操作的关键步骤。执行后会显示类似：

+------------------+-----------------------+--------------+------+
| Table            | Column                | Replacements | Type |
+------------------+-----------------------+--------------+------+
| wp_posts         | post_content          | 152          | SQL  |
| wp_options       | option_value          | 8            | PHP  |
+------------------+-----------------------+--------------+------+

Type 列显示 PHP 表示该字段是序列化数据，WP-CLI 会感知并正确处理。

第五段：人工确认 ​

bash
if [ "${CI_YES:-0}" = "1" ]; then
    echo "检测到 CI_YES=1，跳过人工确认。"
else
    read -r -p "确认正式执行替换？此操作不可撤销（输入 y 继续，其他键取消）：" answer
    case "$answer" in
        y|Y|yes|YES) ;;
        *) echo "已取消。备份保留在：$PRE_BACKUP"; exit 0 ;;
    esac
fi
  • CI_YES=1 用于 CI/CD 流水线自动化执行；
  • 人工执行时必须输入 y 确认，防止误触。

第六段：正式替换与跳过 guid ​

bash
wp_cli search-replace "$OLD_URL" "$NEW_URL" --all-tables --skip-columns=guid
  • --skip-columns=guid：跳过 wp_posts 表的 guid 列。guid 是文章的「全局唯一标识」，RSS 阅读器用它判断文章是否已读。替换 guid 会导致订阅者收到所有旧文章的重复推送。WordPress 官方明确要求迁移时保持 guid 原样。

第七段：刷新缓存与重写规则 ​

bash
wp_cli cache flush
wp_cli rewrite flush
  • cache flush：清空对象缓存（Redis/Memcached），防止旧 URL 被缓存；
  • rewrite flush：重新生成伪静态规则，避免新域名下文章 404。

35.8 常见问题汇总 ​

图片 404（URL 替换不完整） ​

现象：文章能打开，但图片显示 404。

原因：search-replace 只替换了 wp_posts 表中的 post_content，但某些主题或插件把图片 URL 存在了其他位置（如 wp_postmeta 的 _wp_attachment_metadata，或页面构建器的自定义表）。

解决：

  1. 确认使用了 --all-tables 参数；
  2. 检查是否有页面构建器（Elementor、Divi 等）的自定义表需要单独替换；
  3. 参考 第 36 章 处理序列化数据中的 URL。

样式丢失（siteurl/home 协议不一致） ​

现象：前台能打开，但 CSS/JS 加载失败，页面「裸奔」。

原因：siteurl 是 https:// 而 home 是 http://，或浏览器混合内容拦截。

解决：

bash
wp option get siteurl
wp option get home
# 两者必须一致
wp option update siteurl 'https://www.example.com'
wp option update home 'https://www.example.com'

登录死循环（cookie domain） ​

现象：输入正确密码后跳回登录页，或提示「Cookies 被阻止」。

原因：wp-config.php 中定义了 COOKIE_DOMAIN 与当前域名不匹配，或 siteurl/home 不一致。

解决：

  1. 检查 wp-config.php 中是否有 define('COOKIE_DOMAIN', 'old.com');，删除或改为新域名；
  2. 确认 siteurl 与 home 一致；
  3. 清除浏览器 cookie 后重试。

本章总结 ​

本章覆盖了 WordPress 迁移的三大场景：

  1. 本地 → 服务器：以 Docker 环境为源，完成导出、传输、导入、URL 替换、验证的完整流水线；
  2. 服务器 → 服务器：通过 DNS TTL 调低、双机并行、维护模式实现零停机切换；
  3. 只换域名：简化流程，仅需 URL 替换与虚拟主机配置。

同时介绍了 Duplicator 与 All-in-One WP Migration 两款插件的点击级操作，并逐段精读了 ./examples/bin/migrate.sh 脚本，理解其自动备份、dry-run 预演、序列化感知替换的核心机制。迁移后的 8 项验证清单是确保无遗漏的关键。下一章将深入讲解数据库迁移中最容易踩坑的序列化数据问题。
